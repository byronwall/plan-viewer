## Using the viewer

Run `npm run viewer` in the workspace, then open `http://127.0.0.1:4173` (or the configured `port`). `plan-viewer serve` runs the server under `node --watch`, so it restarts itself when the viewer's own code changes (a pull, or an edit to a `*.ts` file); set `PLAN_VIEWER_WATCH=0` to run it without watching. When the viewer is out of date, a button appears in the bottom-right corner: **Update viewer · N new** when `origin` has commits the checkout lacks (it runs `git pull --ff-only` and restarts the server), **Restart viewer** when the checkout moved past what the server is running, and **Reload viewer** when the page is older than the server. The viewer fetches `origin` at most every five minutes and checks on load and every five minutes after; a pull that can't fast-forward shows git's error instead. `npm run demo` in the viewer's repository runs the same `serve` against `examples/workspace/`. Edits to Markdown never restart it: they refresh the open page in place. The viewer opens today's plan, presents milestones and Markdown sections as work cards, and can load a complete card plus commentary into a new Codex draft for review. The Tasks route lists unfinished repository tasks separately and opens each through the normal document reader and Codex draft flow. Task links in plans render current summary metadata from the authoritative task file. The rail's page links each show the one number worth knowing, amber when it needs you: documents changed today (Activity), due check-ins or else open tasks (Tasks), document counts (Topics, Reference), PRs awaiting your review or else your open PRs (Code), your issues in progress (Issues), and threads with new replies (Slack). Hovering or focusing a link shows a card with what sits behind it: the latest changed documents, check-ins then active and open tasks, review requests then your PRs with their review state, your issues by status, or the newest Slack threads. The pointer can move onto the card, and each row opens its item in an overlay over the page you're on (documents and tasks in the document peek, PRs, issues and Slack threads in their overviews); with the keyboard, `→` moves into the card, `↑`/`↓` move between rows, `Enter` opens one, and `←` or `Esc` goes back. Below the page links, the rail lists one row per day, newest first, with a hairline between weeks: each row says what the day was about, led by the plan's note for its first scheduled task (else that task's title, or the plan's first work heading for plans without tasks) and a count of the rest. Hovering a row shows the same kind of card: every scheduled task with its current status and the day's note for it, plus the day's other files, each opening in the document peek; clicking the row opens the plan (or the day's only file), and `[` / `]` step to the previous or next day. Topics and Reference have their own list pages. The Activity route (`V`, first in the rail) is one list of everything, newest first and grouped by day: every task, daily file, topic and reference document by its file's modified time (with the sections and line counts an agent changed, when the server saw the edit), every `.draft` diagram by its source's save time (under **Diagrams**, with its task and subtitle; the inspector shows the drawing, and `Enter` or a click on it opens the diagram viewer), every in-scope Jira and Linear issue by its latest synced activity (a comment, a status change) or its `updated` time, every open PR in tracked repositories by GitHub's `updatedAt`, and, with `slack.codex` set, every synced Slack thread on the Slack page by its last message (its channel and citing documents as context, **New replies** when it changed since you last opened it, the inspector showing its opening message and citing documents, and `Enter` opening the thread overlay, where `J`/`K` walk the Slack rows on screen). Each row shows the time and age, a colored source icon, the item with what changed and where it sits (a task's project, an issue's parent, a PR's repository and branch), its state colored by meaning (green done or approved, blue in progress, amber waiting or needing review, red blocked or changes requested; PRs show their checks in a CI column of its own), and who owns it. Avatars are one picture per person across the viewer: `/api/people` joins GitHub commit authors (email, name, login), Linear users, Slack profiles (from a Slack token with `users:read` and `users:read.email`, or without one, from `slack.people` through Codex's Slack connector) and `people` in `viewer.config.json`, so a Jira assignee and the same person's PRs show the same photo (Slack's, else GitHub's, else Linear's). The index is cached in `tmp/people-cache.json` and rebuilt daily. The sticky toolbar filters by source (with counts), words (`F`), **Mine** (your issues and PRs, plus every document), and time: 24h, 7d (the default), 30d or All, or one day from the two-week strip of stacked bars beside it (each bar is labeled with its date, today in bold; click a bar, or `←`/`→` to step days; click it again to clear). Every filter and the selected row stay in the URL. On a wide screen a click selects a row and reads it in the inspector on the right: a document's status, last edit (the lines an agent added) and rendered text; an issue's Issues-page sidebar (owner, parent, planning documents, links, description, latest comments); a PR's review and CI state, reviewers, description, files and commits. `J`/`K` move, `Enter` or a double-click opens the item in full (the document, or the issue or PR overview, which walks the issues on screen with `J`/`K`), `O` opens it in a new tab, `Y` copies its link, and `Esc` clears the filters. The table stays at most 960px wide and the inspector takes the rest of the row, so on very wide monitors the space past them stays empty. Narrower than 1180px, a click opens the item in full. Issues and PRs re-read the server's caches every minute while the page is open. Document tables fit their columns to their content: short columns (names, dates, numbers) take exactly their one-line width, and the rest of the frame goes to the columns whose extra width shortens the table most, so prose columns get the room. Links and code under 28 characters never break; longer link titles wrap inside their cell. A table that cannot fit even at its narrowest keeps readable widths and scrolls sideways with its first column pinned. A table much taller than the window (over about 1.3 times 70% of its height) scrolls inside its frame under a sticky header, so the page can scroll past it. Its footer shows the rows in view ("Rows 13–24 of 158"), **Show all N rows** (and **Collapse**, which brings the table's top back into view) and **Expand**. The same two buttons sit in a tab on the table's top edge, always shown on a tall table. That tab is sticky below the document dock, so while you scroll through a table with every row shown, **Collapse** and **Expand** stay in view. Hovering a Markdown table shows **Copy** buttons (Markdown source, a real HTML table, as if selected and copied off the page, CSV, TSV for spreadsheets), **Download CSV** (named for the table's heading) and **Expand**, which opens the table full-viewport with its columns fitted to their content, a sticky header and first column, and the same copy and download buttons. In the expanded table, click a header to sort (again to reverse, a third time to clear; Shift-click adds a tiebreak, numbered in the header). Number, percentage and date columns sort by value, blanks always last, and numbers align right. The row under the headers filters each column: plain text matches anywhere (text columns suggest their values), `=x` matches exactly, `!x` excludes, and `> < >= <=` compare numbers, dates or text. **Filter all columns** (`/`) keeps rows that contain every word typed, and matches are highlighted. Escape clears the focused filter before it closes the table, and **Clear** resets every filter and sort. Drag a header's right edge to resize a column; double-click it to fit the column to its content. Copy (except Markdown, which is always the source) and Download CSV take the rows showing, in their current order. A list item keeps the lines indented under it, such as a paragraph or a fenced code block, and a numbered list keeps counting across them and starts at its first number. `plan-viewer lint` reports a fence indented outside a list item, which renders as text, and a fence that is never closed. Hovering a fenced code block shows **Copy** (the verbatim source) and **Download** (named for its heading, with an extension from the fence's language). A `text` (or unlabeled) fence that holds a box-drawing tree, the **Feature scope** format of shape briefs (a root line, then `├── `/`└── ` branches under `│   ` rails), renders as an outline instead: guide lines connect each branch, a `Label: detail` item sets its label in bold, and wrapped lines indent under their item. Top-level branches in capitals (`PLANNED ADDITIONS: first release`, `EVALUATE BEFORE COMMITTING`, `LATER POSSIBILITIES`, `EXISTING`) become sections with a colored dot (blue planned, amber evaluate, gray later, green existing), the note after the colon, and a count of their leaf items; the root line totals them. A section with more than three items flows into two columns when the block is wider than 760px. **Text** in the hover tab shows the source fence instead; **Copy** and **Download** still copy the source. Any line that is not part of the tree keeps the fence as code. Each section heading has **Copy** beside **Open in**, which copies that section's Markdown, heading included.

Press `T` to return to today’s plan, `I` for Issues. Each document section's header has **Copy** (the section's Markdown under its heading), **Copy prompt** and **Open in Codex**. **Copy prompt** puts on the clipboard the prompt the agent draft would have opened with, for pasting into a chat that is already open instead of waiting for a new one. It sits beside **Cancel** in every draft dialog (sections, documents, selections, the global draft, next actions and work items), carrying whatever you typed, and in the Slack thread composer; with nothing typed, the prompt ends at the commentary heading, so the request you type after pasting lands under it. PR panels and overviews (on Code and in worktrees) have a **Copy** row under the agent row: the same skill icons, each copying that skill's prompt (the number keys still open the agent row's drafts). The issue inspector and overview list each issue skill by name with its number key, and a copy icon at the end of each line (on hover) copies that skill's prompt. One-click agent buttons also copy their prompt on `⌥`-click: PR review skills, PR note **Post as review** and **Work through**, a PR comment's discuss icon, issue skills, and worktree cleanup's **Agent review**. Initiatives keep their own copy icon. Press `C` while hovering over a work card, action or document section to open its Codex prompt (over either copy button too: `C` never copies); outside those targets, `C` opens a draft that names the open document (and its task ID for a task file), or carries no context only when no document is open, such as on Tasks or Code. With text selected in a document, `C` opens a draft for that file that quotes the selection and names the section it starts under (`Findings › c4574f89: …`), so the agent works on just that excerpt. `D` opens a draft for the current file, `[` / `]` open the previous / next day's plan, `P` / `N` step to the previous / next document of the open task (the task itself, then its `TASK-NNNN-assets/` documents in the Documents panel's current sort, wrapping from the last back to the first; a `‹ 3 of 14 ›` stepper beside the breadcrumb does the same by click), `A` opens Tasks, `V` opens Activity, and `J` / `K` move to the next / previous document section. `⌘K` (or `Ctrl+K`) and `/` open document search in an overlay (`⌘K` works over the PR overview too, and opening a document from there closes the overview), with arrow keys to select a result and Enter to open it. Search matches titles, paths, task metadata, and each task's work breakdown items (Enter opens the task with that item's dialog) without filtering the sidebar. Matching is a little fuzzy: a word of four or more letters also matches when its letters appear in order in runs, so `sweepf` finds “sweep findings” before you know whether a space or dash comes next, and one mistyped letter in five is forgiven; matches as typed always rank above fuzzy ones, and fuzzy matches with fewer breaks rank higher. A query ranks every kind on one scale: an exact ID or key first, then the query in a title, then terms at the start of title words; live work (open or active tasks and items, open PRs, in-progress issues) rises, finished work sinks, recent edits rise, and yours rises. The eight best of any kind lead under **Top results**, and the rest follow grouped by kind (Tasks, Work items, Issues, Pull requests, Initiatives, Pages, Documents), kinds ordered by their best remaining match. A **Pages** group lists Today, Tasks, Topics, Reference, Plans, and each Code tab (Pull requests, Worktrees, Commits, Cleanup), so typing `pull` jumps straight to the PR list. **Local servers** (also in Pages) opens an overlay listing every local server the viewer started (`code.run`): its worktree, branch, URL, command, start time and live output, with Open (`Enter`), Restart (`R`), Stop (`S`, or Dismiss once it has exited) and the worktree overview (`W`). With no query, the palette leads with open PRs that need your review and your own open PRs. A PR number (`1938`, `#1938`, or `Orbit#27`) or words from a PR title, branch, or author list matching pull requests from tracked repositories, open or closed. Enter opens the PR overview and `⌘Enter` opens the PR on GitHub. The highlighted PR is fetched in the background, so the overview usually opens instantly. `H` (or the clock button in the bottom-right corner) opens **Recently viewed** from anywhere, including over the PR overview: every page and PR or worktree overview this browser has shown: `↑`/`↓` and Enter, or `1`–`9`, go back to one and reopen its overview. A work item you opened is its own row (its ID and title, with the task beneath), so it reads apart from the task page; switching its Item/Graph view doesn't add another. A row under **You are here** names the list on screen, **Recently viewed** (where it opens) or **Recently changed** (documents edited outside the viewer), each with its count; `Tab` or a click anywhere on that row flips to the other, and `1`–`9` number the open list's rows. The filter covers both lists, so the counts show where the matches are, and an empty list says when the other one has some. It opens with focus in its filter, so typing narrows the list at once (so `H` then `snow` narrows to matching places, and `h` is just a letter there); Escape clears the filter, and a second Escape closes the menu. Closing an overview also shows a toast with **Reopen**. The star at the top right of every page, and beside the close button in the PR, worktree, issue and initiative overviews, favorites whatever is open: a document, task, work item, page, PR, worktree, issue, or initiative. It's filled once favorited; click it again (or press `⌘D`/`Ctrl+D`, which works over the overviews too) to remove it. A favorite is keyed like Recently viewed, so a PR is one favorite whichever file was open. A toast confirms each change with **Undo**. **Favorites** at the top of the sidebar lists them, newest first, with the current one highlighted; clicking one reopens it as you left it (with its overview). Favorites live in this browser's local storage. Press `?` (`Shift+/`) or click **Keyboard shortcuts** for the full guide: one screen, grouped into Go to, Read, Find and keep, Agent drafts and General, with paired keys (`J` `K`, `N` `P`, `]` `[`) on one line and only this platform's modifier shown. Letter shortcuts pause in typing fields and open dialogs. Escape closes overlays; a Codex draft containing text stays protected until opened or explicitly canceled.

The viewer is local-only and dependency-free beyond Node.js and Codex Desktop on macOS. It watches authored Markdown under `daily/`, `tasks/`, `plans/`, and `reference/` and refreshes the active document and library in place when those files change. All viewer tabs share one live-update connection (one tab holds it and passes changes to the rest), so any number of tabs can stay open: a browser allows only six connections per host, and a connection per tab used to stall every request once six tabs were open. When a file changes from outside the viewer (an agent you handed work to, or your editor), a toast names the document, the sections the changed lines sit under, and how many lines came and went (`+3 −1`); **Open** (or **Show** for the document on screen) jumps to the first changed section. A burst of writes to one file updates its one toast. In the document itself, the lines an agent added or rewrote keep a light green tint until you open another document, and the first time they render (live, or from the toast) they and their sections flash once. Lines are found by their rendered text, so one that renders differently from its source, such as a task reference or a next action card, gets only the section flash. Recently viewed (`H`) lists the last eight changed documents under **Recently changed** (`Tab` from **Viewed**), and keeps them since the server started. Status changes made in the viewer itself don't toast. It omits folders listed under `exclude` in `viewer.config.json` (such as a generated issue corpus) from the document rail and live watcher. Opening a draft uses the native `codex://threads/new?prompt=…` handoff in the workspace's Codex project, but never submits it. Review or edit the prepared message in Codex Desktop and click Send there when it is ready. The server prints structured `codex-dispatch` logs for validation, draft opening, and failures. Press Enter in the viewer feedback field to open the draft; use Shift+Enter for a new line. Paste or drop images into a draft field to attach them: neither app's deep link carries attachments, so the server saves them to the workspace's ignored `tmp/handoff-images/` and the prompt lists their paths for the agent to open.

### Tab briefs

An agent that opens a viewer tab for you can say why with `brief=<Markdown>` in the URL, beside whatever else the tab opens (`path`, `diagram`, `pr`, `issue`): for example `/?path=tasks%2FTASK-0101.md&brief=…`, built with `encodeURIComponent`. The first line is the title; the lines after it are the body, usually the ask, the decision waiting, and links. It renders like a document, so task, PR and issue keys become links, and `[Next actions](#next-actions)` names a section of the document the tab opened on. The brief floats at the top centre of the page, above any overlay, so it never moves the page under you. Clicking a section link closes any overlay and scrolls to that section; clicking another document opens it.

× hides the brief to a chip in the bottom-left corner that shows its title; clicking the chip opens it again. The brief belongs to the tab, not the URL: it leaves the URL once read (so favorites and Recently viewed stay clean) and stays in the tab's session storage, so it survives navigation and reloads, and a hidden brief stays hidden after a reload. A URL with a different brief replaces it and opens it.

## Code view

The Code route (`G`, `?view=code`, opening on Pull requests) is a control center for the repositories listed in `reference/code-repos.json` (`code.reposFile`); add or drop one from the gear menu beside the refresh button. Summary tiles across the top (live today, uncommitted, review requested, my PRs with failing CI, open PRs, safe to remove) jump to the matching filter, and a 30-day activity strip filters worktrees to a day when clicked. Selecting a row opens a detail pane that starts with the same label/value grid and icon rows as the overview's left column (status, author, branch, size, reviewers, review skills, worktree actions; for a worktree its path, ahead/behind, history, PR and cleanup reason), then commits, changed files, and ignored hand-made files. The expand icon beside the title opens the overview. `J`/`K` or the arrow keys move, `Enter` or a double-click opens the overview for a worktree or PR (or a commit's diff), `E` opens the worktree in the configured editor (`code.editor`, VS Code by default), `X` opens the configured terminal (`code.terminal`), `L` starts or stops the local server (`code.run`), `S` starts a new agent session, `Y` copies the path or link, `1`–`N` draft a configured review skill, and the key after them drafts an open **Discuss** prompt about the PR for you to finish, `F` focuses the filter, and `R` rescans everything, like the refresh icon.

- **Worktrees** lists every worktree newest first, by the latest of its creation, last commit, and uncommitted edits, with a recency dot, ahead/behind counts against main, PR and CI state, and icons for the editor, terminal, Finder, a new agent session, and the branch on GitHub. Under the branch sits its PR title, or else the head commit when it belongs to the row (a commit made on the branch, a detached HEAD, or the main checkout). A detached worktree is named by its short SHA (click to copy). **Folder** is one line: where the worktree sits (`main checkout`, a folder inside the repo such as `.claude`, a home folder such as `.codex`, `tmp`, or the folder beside the repo) and the segment that names it, left out when it only repeats the branch; a temp copy whose path embeds another worktree's path reads `↳ <that worktree>`. Click copies the full path, and the tip and detail pane show it. **Group** sorts into Changed (day, week, month), Repo, or Folder buckets, remembered per browser.
- **Pull requests** lists every open PR with CI, review decision, comments, labels, conflicts, size (lines added over lines removed, three digits at most, such as +1.23K −87; exact counts on hover), and author. **Open** / **Merged & closed** switches to each repo's 60 most recently merged or closed PRs, newest close first, with a merge or × icon in the State column and the close time under Closed. Filter by All / Review requested, author, drafts, or failing CI, and sort by updated, oldest, or largest. A PR whose base is another open PR's branch is drawn stacked on it, numbered from the bottom; a PR from the repository's default branch (a release PR such as `main` → `deploy/staging`) never counts as a stack base. **Authors** (`A` on the Pull requests and Commits tabs, where it replaces the global Tasks shortcut) picks one or more people, you first and then by activity; clicking an avatar in a row filters to that person, and the pick follows you between the two tabs and stays in the URL (`&author=`). Every author shows the same mark in both tabs: their GitHub avatar over initials. With more than one tracked repository, every row on every tab starts with a two-letter repo mark on that repo's own hue (initials of its name, made unique). **Repos** (`G` on the Code page, where it replaces the global Code shortcut) is the legend: every tracked repository with its mark and how many rows it has on the current tab (repos with none sit below, under their own heading), and the place to filter to one or more of them, by mouse or with ↑↓, Enter, and Shift+Enter for only one; clicking a row's mark does the same, and the pick stays in the URL (`&repo=`). Worktree paths then drop the repo's own folder, since the mark already names it. The gear in the toolbar opens **Tracked repositories**: a path box to add one at the top, then every tracked repository on one line with a delete icon. The panel stops at the bottom of the window and its list scrolls. Commits are matched to GitHub logins by noreply address, your own `user.email`, or by asking GitHub who wrote one of that email's commits, so a person with two git names is one author. The icons draft the review skills configured under `code.prSkills` in Codex or Claude Desktop (toggle at top right), in the PR's worktree when one exists and the main checkout otherwise. Drafts wait for you to press Enter; Claude asks once to trust a folder opened this way.
- **Cleanup** sorts worktrees into safe to remove (clean, with a merged or closed PR, a branch merged into main, or never used), review first (clean, no PR, idle two weeks), too new, and keep. "Skip if touched within" keeps worktrees created or touched in the last day or week out of the removable groups. Remove runs `git worktree remove` in small batches with a progress bar; it keeps branches and git refuses dirty trees. Agent review drafts a prompt that checks the selected worktrees first.

The **PR overview** (from ⌘K, `Enter` on a PR, or the expand icon in its detail pane) is a full-screen overlay. Its left column opens with one label/value grid: status (CI, review decision, conflicts), author, branch, size and labels, and reviewers (bots as an avatar only, every state named on hover), then one icon row of review skills (`1`…`9`), an **Open** row (the signed-in PR deployment when `code.prPreview` is set, copy link `Y`, GitHub), and one of worktree actions, led by the worktree overview (`W`), with the local server (`L`, `code.run`; on a PR without a worktree it checks one out first), editor, terminal, Finder and a new agent session. The overview has everything the PR's Code page row has, even when opened from another page (⌘K, a document, Activity). Every icon is named on hover. Below sit **Linked**, the planning documents (tasks first) that link the PR's GitHub URL or name a tracker key from its title or branch (`MOD-123`, `alex/mod-123-fix`), each read in a document peek over the overlay (`Enter` there opens it in full); then notes, each commit to walk (`N`/`P`), and the stack (click any row); then the changed files and the diff. The view toggle (**Description**, **Changes**, **Stack**; in a worktree **Local**, **Changes**, **Uncommitted**) sits in the header above the diff it switches, beside **One file / All files** and **Split / Unified**; the keyboard icon there lists every shortcut on hover. A PR or stack in a tracked repository is read from its local clone: its head and base commits are fetched by SHA only when missing (no branch or ref changes), and the diff, whole files and line counts all come from git, so even PRs over GitHub's 300-file or 20,000-line diff limit load. Other repositories use GitHub. **One file** steps through files with `J`/`K`; **All files** (`V` toggles) stacks every file in one scroll, rendering each as it nears view and holding files over 1,500 changed lines behind a click. **Viewed** checkboxes work like GitHub's: `X` marks the current file viewed and moves to the next unviewed one (wrapping to the top of the list), the header counts progress, viewed files collapse in **All files**, and a file that changes afterwards comes back unviewed with an amber ● in the file list (hover the Viewed box or the dot for when you checked it; stored per browser). Opening a note from the PR column unchecks its file, so the note is on screen. Symbolic links get a `link` badge and show their target path instead of a one-line text diff. Lockfiles, snapshots, and vendored or minified files start collapsed; the chevron toggles any file. `/` filters the file list, and viewed files drop out of the list and `J`/`K` by default; `U` (or the count beside the filter) shows them again. Once every file is viewed the whole list returns, with "All N files viewed." under it. `S` switches split/unified. The expand icon beside the close button (or `G`) widens the overlay to fill the whole window, edge to edge, for more room beside the map; it stays wide on later opens until toggled back (stored per browser). **Map** (beside the filter, or `T`) swaps the file list for a treemap of the change: folders as nested boxes, each file sized by its line count (from a local clone; lines changed otherwise) and filled from the bottom by its changed share in green and red, added files green, deletions hatched red, and each rename left as a hatched ghost at its old path. The **Moved** row lists renames bundled by folder (`docs/ → client/ 13`); hovering one, or a renamed tile, outlines its old and new folders and fades the rest, and clicking pins it. **Edges** (`E`) adds a ribbon per move. Hover a tile for its old path, status and line counts; click it to open its diff; click a folder label or breadcrumb to zoom (`Backspace` zooms out). The copy and download buttons export the map at the current zoom as a titled PNG, ready to paste into a PR. Expand (`F`) lifts the map over the whole overview in a frame you can resize from its bottom-right corner, so **Copy image** captures the shape you choose; `F` or `Esc` shrinks it back. Where the browser blocks image copying, the PNG downloads instead. Drag the divider between the map and the diff to give either side more room (double-click it to reset); the split is kept as a ratio, so it holds as the window resizes, and is remembered per browser. In a stacked PR, `[` and `]` move to the PR below and above in the stack. **Stack** (beside Changes) shows one diff for the entire stack, from the bottom PR's base branch to the top PR's branch; notes stay per PR, so they can't be added there. The description renders GitHub's raw `<img>` and `<details>` tags; images attached to the PR are fetched once through `gh` (signed in) into the workspace's ignored `tmp/github-images/` and served from there. The PR overview opens on the Description; while it stays open, moving to another PR (`[`/`]`, a stack row, a linked PR) keeps the view you picked (a commit becomes Changes), and closing it resets the next open to the Description. On a PR, `D` always opens the Description; in a worktree it cycles Local, Changes and Uncommitted. Under the description sit the PR's comments, oldest first: conversation comments, line comments (file and line, full path on hover) and review summaries, skipping bare approvals. Bot comments (CI, Copilot, linkbacks) are hidden behind **Show N bot comments**. Each comment's discuss icon drafts a prompt in the configured agent app that quotes the comment, links it, and names the PR's worktree, ready for you to finish and send. Changed words inside a changed line or paragraph get a darker mark, and syntax colors come from both whole files (PR diffs included), so a docstring or comment that opens above a hunk stays shaded as one. Changed lines show their indentation and trailing whitespace as faint dots (spaces) and rules (tabs), and a change that only re-indents gets a lighter mark. On a PR, select code and press `C` (or click **Comment**), or click or drag down the line numbers, to keep a local note in `plans/pr-notes/` (`code.prNotesDir`; `Enter` saves, `Shift+Enter` adds a line); notes appear under the code they cover and in the PR column, where **Post as review** and **Work through** draft agent prompts over the draft notes. Each note keeps the code it quoted, so after new commits it follows that code: **moved to N** when the code shifted, **edited** when at least half of the quoted lines survive in one place (the note sits there), and **outdated** (red, counted in the Notes header) when the code is gone from the diff, which puts the note at the top of its file. A whole-file note records the file's diff and shows **file changed** once it differs; an older whole-file note without that record shows it when a PR commit dated after the note touches the file (a rebase restamps commits, so it marks every file the rebased commits carry). The PR column lists each note in full, with a × on hover to delete it. Edited, outdated and file-changed notes count as stale: **Stale N** shows only those, and **Clear N stale** (click twice to confirm) deletes them all, clearing the way for a fresh round of review. Drag the PR column's right edge to widen it (double-click to reset; remembered per browser). The open PR is kept in the URL (`?pr=owner/repo#n`), with the current file (`&file=`) and commit or other scope (`&scope=`), so a refresh reopens the same view. `R` (or the refresh icon in the header) re-reads just this PR from GitHub, its details, checks, comments, diff and notes, and stays on the same file and view, without rescanning the Code page.

The **worktree overview** (`Enter` on a worktree, **Open worktree overview**, or **Worktree overview** from a PR that has a local worktree) browses a worktree like a PR in the same overlay. The left column uses the same grid: the path, ahead/behind, the branch's PR (click or `W` to open its overview), review skills, and the worktree actions. **Changes** is everything since the fork point, committed or not, plus new files, measured against the PR's base branch when the worktree has an open PR (so a stacked branch matches its PR) and against main otherwise. **Uncommitted** and each commit follow. **Local files** lists what no commit carries: untracked files and folders, and hand-made ignored files (dependency and build caches are left out), with size and age. Folders expand to their files; an untracked file opens in its diff, and an ignored one opens read-only in place (Markdown rendered, up to 2 MB). The URL keeps `?wt=<path>`. `R` re-reads just this worktree: its commits, files and diff.

Dirty checks, CI, and PR history take about 15 seconds and load in the background; the refresh icon (or `R`) forces a rescan. Each PR's details and diff are cached on the server until the PR's updatedAt changes. Open PRs, PR history, and CI are cached in `tmp/code-cache.json`, so the Code page and ⌘K answer immediately after a restart. The server refreshes them every 10 minutes, and a request that finds the open-PR list more than a minute old returns the cached list and refreshes it in the background.

## Plans

The Plans route (`M`, **Plans** in the sidebar, `?view=plans`) lists the initiatives on each tracked repository's `origin/main` (its remote default branch): every `initiative-map.json` outside hidden, dependency, build and vendor folders, with the Markdown files beside it. The page works like the Code view: a toolbar on top, one dense table, and an inspector beside it on wide screens (1600px and up). A modified click still goes to GitHub. Scans are cached by commit in the workspace's `tmp/plans-cache.json`, and open PRs with their changed files refresh every two minutes in the background.

## Steps and the Outbox

The Steps page (sidebar, `?view=steps`) lists every open step of every unfinished task, grouped by **Next move**: **You decide** (approvals, decisions and choices), **You act · friction** (something only you can do, each with why and the fix that would remove it), **Agent**, and **Others**, with **Blocked** (prerequisites not done) and **Needs a kind** behind a toggle in the All view. A step is a work-breakdown line; a leaf step, or a choice. It may end in `{kind, size}`:

```markdown
- W2.1: Comment on ABC-123 [open] (after: W1) {jira-comment, S}
- W3: How the fix lands [open] {pick-one, S}
  - W3.1: On main first — ships now [open] {option, recommended}
  - W3.2: Stacked on the other PR — one review, but waits [open] {option}
```

Kinds are `agent`, `check-in`, `decision`, `byron` (only you can do it), an outbound kind, or a choice: `pick-one`, `pick-any` (options as children, each `{option}` with a ` — trade-off`, one `recommended`) and `do-all` (an ordinary group). Sizes are `S`, `M` and `L`. Without a kind, a step takes its outbound draft's kind (a task asset whose front matter has `step: TASK-0101 W2.1`), else `agent` when a Next action names it, else `check-in` when it is waiting with a prompt. `waiting` means waiting on someone else. An outbound step is **You decide** while its draft is ready, **You act** when it is `send: manual`, and leaves the list once sent or dropped.

Today's plan opens with a **Steps** panel: a thin **You | Agent | Others | All** toggle with counts (You by default; the choice stays in the URL as `&move=`), then the first eight of those steps, one line each with a state pill (**Decide**, **Friction**, **Agent**, **Waiting**), the full title, and the task and step ID on the right. The panel is always as tall as its fullest segment, so switching never moves the page. A row opens the step dialog over the plan; **All N on Steps →** goes to the Steps page. `plan-viewer lint` checks steps too: kinds must be known, a `[waiting]` step can't be one that waits on you (`decision`, `byron` or a choice), a choice needs two or more `{option}` children with exactly one `recommended` until it is decided, open steps of tasks created on or after `steps.requireSizeFrom` need a size, no prompt may contain a `steps.forbiddenInPrompts` word, and an outbound draft's `step` must exist in its own task and agree with it (a sent draft's step completed, a completed step's draft sent or dropped).

The inspector's actions remove what would otherwise be friction. **Start** on an agent step runs `steps.start` as a local agent session with the step's prompt (or its title and task when it has none), marks the step `active`, and holds one of `steps.slots` slots until the run ends; with `steps.refill`, a finished run starts the next ready agent step that has a prompt. Only runs started here count toward the slots, and a step whose status is `active` without one shows **Agent · in progress**. A `byron` step's machinery file (front matter `kind: byron`, `step`, `run`, `target`, `undo`, `why`, `fix`) shows the statement: a single read-only statement gets **Approve and run**, which runs `steps.run`, appends the output to the file, and completes the step; anything that changes data gets only **Copy statement** and **Mark done**, since the viewer never runs it. A machinery file with `apply:` (an allow rule for Claude Code) gets **Apply**, which adds the rule once to `steps.settingsFile`, inside the workspace. A `decision` without a choice gets **Mark decided**.

The segmented control filters by next move with counts, the menu by kind (**Outbound** is the Outbox, also in the sidebar), and the selection stays in the URL (`&select=TASK-0101:W2.1`). The inspector shows a choice's options with **Pick** (which completes the choice, defers the options not picked, and adds a dated update to the task), an outbound draft's approval panel, a step's prompt, or what a blocked step waits on. The sidebar counts the steps waiting on you.

**The step dialog** shows one step of any task over whatever page you are on; a step row anywhere opens it, and nothing behind it changes. Its top bar names the task (its status on hover) with its completed count, **Item | Graph**, **Open task** (makes the task the page) and **World** (the task's world). The rail on the left lists the task's steps under a small **You | Agent | All** toggle (You and Agent list only the steps waiting on that mover; All is the whole breakdown as a tree). The right pane has the step's ID, status and state pill with its actions at the top right: the step's own action leads when it has one (**Mark decided**, **Start**, **Approve and run**, **Apply**), then **Send to agent**, then a quiet **Update** (a draft that revises the item in the task file). ← and → step through the items with updates. Then the title, why it is yours when the reason says more than its pill (the friction and its fix, or what it waits on), a strip of what it waits on → the step → what it unblocks, then a choice's options with **Pick**, an outbound draft's approval panel or its machinery, its prompt, the updates filed under it, and other mentions. `?step=TASK-0101:W2.1` reopens it on refresh, Recently viewed lists it, and closing it with Esc or × offers **Reopen**.

## Outbound drafts

A task asset that opens with `outbound:` front matter is a message, comment or issue waiting to go out:

```markdown
---
outbound: jira-comment
target: ABC-123
status: ready
step: TASK-0101 W2.1
send: comment
---

# Comment on ABC-123

Notes for the reader.

<!-- jira:start -->
The text that goes out.
<!-- jira:end -->
```

`outbound` is the kind (`jira-issue`, `jira-comment`, `jira-edit`, `jira-transition`, `slack`, `pr-comment`, `review-request`, `email`), `target` where it goes, `step` the work item it completes, and `send` the kind's flags for the workspace's sender (`manual` when you send it yourself). The text that goes out sits between `<!-- jira:start -->` and `<!-- jira:end -->`, or `<!-- send:start -->` and `<!-- send:end -->`; everything else is notes. `dry_run: true` makes every send of that file a dry run.

The draft's page opens with an approval panel: the kind, target, step, the hash of the text, a status, and the exact text under **Will go out** (the page below shows the notes). **Approve and send** records your click and that hash in the front matter (`status: approved`, `approved: <time> sha=<hash> by=viewer`) and runs `outbound.send`, which checks the hash again before sending; if the text changed since the page showed it, nothing is sent and the draft goes back to **Ready for you** with "Changed since you read it". A sender error leaves it **Didn't send** with the error and a **Retry**. **Send back** opens a box for your feedback, appends it under the notes as a dated section, sets `status: revise`, and starts `outbound.revise` (an agent that revises the draft and sets it back to `ready`, which needs your approval again). **Drop** sets `status: dropped`. A `send: manual` draft offers **Copy text** (as rich text) and **Mark sent** instead, with a note that it is friction. The viewer never sends anything itself; with no `outbound.send`, Approve and send is disabled.

## Tasks, next actions, and links

The Tasks page (`A`) lists unfinished tasks, with a **Steps** column counting each task's open steps by who moves next (`2 you`, `5 agent`, `1 waiting`, one per line, the part waiting on you in the waiting color; sorting by it puts the most waiting on you first) and a **Contents** column counting the documents, diagrams and images in each task's assets folder (sortable by their total); clicking a row reads it in the detail pane, whose **Steps** section shows the task's progress, the same counts, and the steps of the first mover with anything waiting (you first), each opening the step dialog over the page, with **All N open steps →** opening it on the whole list, and a double-click opens the task file. **Show N completed or deferred** adds the rest below them, in the same sort, and `&done=1` keeps that on the URL. It is the same control, wording, and rule as a task's work breakdown. **Waiting** is for work that sits with someone else: it stays tracked but drops below open tasks until it needs a look, then leads the list as **Check in** and counts on the rail's **Tasks** link. Two things bring it back, both computed, so nothing needs re-editing: its check-in date arriving, or something it watches moving. Pick **Waiting** in the status menu (click a status, or right-click a row) for a check-in a week out, or **3d**, **1w**, **2w** or **4w** under it; on a waiting task the same buttons push the date out. The viewer writes `check_in: YYYY-MM-DD` to the front matter (leaving waiting removes it); a waiting task without one checks in `checkInDays` after its `updated` date. It watches the PRs, GitHub issues and Linear or Jira issues its `## Next actions` name, and one counts as moved when its dated state (merged, closed, opened, or the tracker's last update, from the same cache as link titles) falls after the task's `updated` day, so recording a check-in or setting the status again resets it. The detail pane's **Waiting on** lists the check-in date and each watched item with its state, moved ones first and dated; the status's hover says why a task is due.

**World view** (the Tasks page's toolbar, the detail pane's **World**, a task page's dock, or `W`) lays work out by day, oldest at the left, so you can see what a task holds without clicking through it. A task's world has one column per day with activity (quiet stretches are skipped and marked with a dashed line; the columns share the window's width, so a short history spreads out and its thumbnails grow) and one lane each for work, diagrams, images, documents, updates, the daily plans that mention it, and other files in its `TASK-NNNN-assets/` folder. The **Work** lane puts each completed work item on the day of the last update whose title names it (`… (W1.2)`; items no update names stay out), and a wider **Today** column holds the task's steps as the same list as today's plan (the **You | Agent | Others | All** toggle, You first when anything waits on you, eight a segment with **+N more** for the rest); each row, and each completed item on an earlier day, opens the step dialog above the world. Asset files sit on the day they last changed, and a picture exported beside its `.draft` (`flow.png` next to `flow.draft`) is left out, since the diagram stands for it. Diagrams and images show as thumbnails that open the image viewer with the task's whole gallery; documents and plans open a peek, and an update opens the task in the peek at its Updates section, so closing either leaves you where you were; a file copies its path. The all-tasks world lists the Tasks page's tasks (same order, same completed toggle) one per row, each day marked with its newest picture and a dot per kind with its count (work, diagrams, images, documents, updates), and today's work dot counting what is ready; click a mark or a task to open that task's world at that day. **← All tasks** in a task's world (or Backspace, Alt+←, or the mouse's back button) returns to the all-tasks view at the same scroll and zoom, or opens it when you started on the task. **Open task** (or Enter) in a task's world closes every overlay and makes that task the page, however you got there; Back in the browser returns to where you started. Both open scrolled to the newest day at full size and fade days more than two weeks older than it. Drag to pan; pinch or ⌘-scroll zooms around the cursor; **Recent** and **All** reset the frame, and the zoom level resets to 100% when clicked. If the file list can't load, **Try again** sits beside the message. `?world=TASK-0082` (or `?world=all`, with `&world-day=` for the day) reopens it on refresh.

Each task's `## Next actions` contains short action headings and fenced `prompt` blocks. Write each prompt so an agent can advance one bounded step with the supplied repository context and a clear result to verify. An optional `Work item: W1.1` links it to the task's work breakdown. The viewer also gives existing bullet actions individual buttons.

Each action is one row: its work item, a status icon (a check when ready, a lock when it waits on prerequisites), the title, and the first line of its prompt. Click a row (its **Draft** hint shows on hover) to review the full prompt, add optional context, and click **Open in Codex** (or Claude, per the agent picker). Waiting actions open the same way: the row and the dialog say what they wait on (`After W1.2`), but nothing stops you, so you can tell the agent the prerequisite is done or that the action is still good context. The viewer uses the existing desktop handoff with a prepared, editable draft; review it and click Send there. The action prompt and absolute source file path are included. Additional context is optional; when given, it appears above the stored prompt and takes precedence where they differ. The server rechecks that the stored action hasn't changed before opening the draft. This local handoff expects an agent with access to the planning workspace.

A daily plan's **Scheduled tasks** section shows as one panel: a row per task bullet with its short number, its title, the plan's note for it in full (muted, with its PR, issue, task and Slack references as links; a click on a link follows it), and on the right its open steps counted by who moves next (`3 you · 5 agent · 1 waiting`, zeros left out). A waiting task says so in italics before its counts (`on hold, check in Nov 20`); a completed or deferred one shows only its status. A bullet that links several tasks before its note is one row for the first; the others lead its note as links. Clicking anywhere else on a row opens the step dialog on that task at its first step waiting on you, else its first ready step, with the rail on that mover. Other lines in the section render below the panel. A plan can also contain its own `## Next steps` action prompts for day-specific work; those still show, and they are what the dock's count covers. Task actions stay in their task files.

Use `## Work breakdown` to record the full known scope as nested bullets:

```markdown
- W1: Deliver the outcome [open]
  - W1.1: Reproduce the behavior [completed]
  - W1.2: Implement the fix [open] (after: W1.1)
  - W1.3: Verify the result [open] (after: W1.2)
```

IDs are unique within the task. Statuses are `open`, `active`, `waiting`, `deferred`, and `completed`. Nesting describes the scope; `after` describes prerequisites. A task page shows its work breakdown as one **Steps** panel in its place (its `## Next actions` section is not shown on such a page; the prompts there show in the step dialog). The panel has the same thin toggle as today's plan with this task's counts (**All** by default, so the whole open scope reads as an outline; `&move=` keeps another choice), then every step under a light header line per workstream (a top-level item; click it to read that item): its ID, status icon (a check when ready, a lock when it waits on prerequisites), a state pill only when it waits on you, the full title, and on the right a note count and `ready`, `after W1.2`, `active`, `running` or `waiting`. A step is a leaf, a choice, or an open item whose children are all done. Completed and deferred steps hide behind **Show N completed or deferred** at the bottom. **Graph** in the panel's header opens the dependency graph in a popover under it, with arrows from prerequisite to dependent and an expand control for a full-window view (clicking a node opens the step dialog); **World** opens the task's world. Clicking a row opens the step dialog over the page, and `C` over a row drafts that step for an agent. An update whose bold title names a work item, such as `- **2026-10-23 — Delete list (W2.3):** …` with nested bullets under it, is filed under that item, and its row and node show a note icon with the count. In the dialog, **Send to agent** opens a draft that advances the item (with its stored action prompt when it has one), and **Update with agent** opens one that revises the item in the task file (title, status, nesting, prerequisites, linked action) without doing the work. Both work on every item; when the item is not ready they turn yellow, and the draft tells the agent what the item still waits on. **Item | Graph** in the dialog's top bar (or `G`) swaps the item pane for the task's whole dependency graph with the open item outlined, centered whole when it fits and on the open item when it does not; drag to pan (past the graph's edges, so any part can sit anywhere on screen) and scroll to zoom around the cursor, with the zoom kept as you move between items. The toolbar in the graph's corner has − and + (or the `-` and `=` keys), the zoom level, which resets to 100% when clicked (`0`), **Fit** to show the whole graph, never above 100% (`F`, or double-click the background), and **Item** to center the open item (`C`); clicking a node or a group's header reads that item, and the choice sticks across opens (`&graph=1`). Only Esc or × close the dialog, and backing out of a Send or Update draft returns to it; J and K walk the rail, ← → the nearest items with updates (from any item), and `&step=TASK-0101:W2.3` in the URL reopens it on refresh or from ⌘K (an older `&item=W2.3` on a task's page still opens it). Items that are completed or deferred, along with everything under them, are hidden from the Steps panel and graph until you check **Show N completed or deferred**; `&done=1` keeps that choice on the URL and carries it from document to document. Missing dependencies, duplicate IDs, and cycles produce warnings; readiness may be wrong until they are fixed, but actions still open.

Run `npm run lint -- tasks/TASK-0001.md` after authoring or updating a planning document, or `npm run lint` to check the full authored corpus. It rejects invalid task front matter, work-breakdown warnings and action references to missing work items using the viewer's parsers. Point the workspace at the shipped pre-commit hook (`plan-viewer init` adds the `prepare` script that does this; see the README). The hook validates the staged contents of changed planning Markdown files, so a corrected working copy cannot hide an invalid staged version. Its link check also runs against the index, so files another session has not staged yet cannot block a commit. Valid work that is waiting on prerequisites passes lint. The viewer itself never refuses to load over one bad task file: a task whose front matter doesn't parse (a placeholder an agent wrote to reserve its ID, say) is listed under Reference as **Invalid task** and opens as plain Markdown until it is fixed.

Tasks and daily plans can record related conversations under `## Chats` using ordinary labeled Markdown links. The viewer shows recorded chats above the document, in the selected task's detail pane, and alongside task references in daily plans. ChatGPT conversation links open in the browser; `codex://threads/<thread-id>` links open the existing chat in Codex Desktop, and Claude Desktop session links (`claude://claude.ai/epitaxy/local_<id>` or `claude://session/local_<id>`) open that session in Claude. Keep links in the authoritative task so daily plans pick them up without copying them. The viewer recognizes conversation links elsewhere in the prose too, while ignoring fenced prompts and inline code examples.

Viewer handoffs ask the receiving agent to record its verified conversation URL or thread ID when available, and the workspace's AGENTS.md can give agents the same convention. The new-draft handoff does not return a thread ID, so the viewer cannot automatically know the resulting conversation. An agent with trusted session identity can save it; otherwise paste the conversation's actual URL into `## Chats`. Shared snapshot URLs do not provide a place to send follow-up commentary and are not shown as related chats.

Documents get a clickable breadcrumb (task list, day switcher, parent document, or copy target) and a sticky bar with a Codex draft button and panels. **Work** (completed items as a ring and count) shows the task's Steps list, and its **Work items** button opens the step dialog at the first ready item; a document with next actions but no work breakdown shows them as **Next actions** instead. **Updates** lists the task's updates. **Diagrams** (when there are any) shows the diagrams the page embeds, then the task's other `.draft` files marked **Not embedded**, as thumbnails that open the diagram viewer. **Links** groups the outgoing links by source, and its last tab, **Linked from**, lists the documents that link here. A task with files in `tasks/TASK-NNNN-assets/` (and each of those files) gets a **Documents** panel: the task first, then its documents newest first under day headings, each with its `##` sections, when it was last edited (minutes or hours ago today, the time of day before that), its word count and images. **Edited**, **Created** and **Name** in the panel header re-sort it, and the choice is remembered in this browser; hover a row for its file name and exact edit and creation times. Standalone `TASK-0001` references, PRs (`#1810` in `github.defaultRepo`, `Orbit#2738` for a repository in `github.repos`), tracker keys such as `ATL-2845` (from `trackers`), slash lists such as `TASK-0016/0017` or `ATL-2733/2734`, commit SHAs (`Orbit@052702c8`, or bare SHAs inferred from the paragraph's PR references; not in headings, where a leading hex ID such as `### c4574f89: Connection dropped` names the section), 32-character trace IDs (through `traceUrl`), and Slack permalinks become icon links. Slack links open in the desktop app, or, with `slack.codex` set, in a thread overlay read once through Codex's Slack connector (a couple of seconds, no model) and then from the cache in `tmp/slack-threads.json`. The overlay reads like Slack: the channel name, who started the thread and when, the reply count and the people in it; day dividers; one header per run of messages from the same person within five minutes; emoji, skin tones and reactions (a workspace's custom emoji stay as `:name:`); mentions; and a **New since you last read** divider (`N`) from the last visit in this browser. The linked message is highlighted and scrolled to. **Linked from** lists the tasks and plans whose Slack links point into the thread, and each cited message carries the citing document's ID. **Links** (`L`) opens the documents' link browser over every link in the thread, with titles and states. Find (`F`) highlights matches and dims the other messages; `Enter` and `Shift+Enter` step through them. The box at the bottom (`D`) opens a Codex or Claude draft (whichever the agent picker chooses) in the planning workspace, with the thread saved to `tmp/slack-threads/<channel>-<ts>.md` for the agent to read and the citing documents named; typed text keeps the overlay open on `Esc` and backdrop clicks. `O` opens the thread in Slack (each message's ↗ opens that message), `R` reads it again (keeping your place), and `Esc` closes the overlay (or just the Links panel when it is open). The open thread is kept in the URL as `?slack=<permalink>`, so a refresh reopens it; closing it offers Reopen, and Recently viewed lists it by channel and first line. `⌘D` (or the header star) favorites the thread as opened, and each message's hover star favorites that message, which reopens the thread scrolled to it. Messages show their attached file names (open the message in Slack to see the files). A forwarded or shared message shows as a card under the message that shared it: its author, channel and date, and its text; a click on its header opens that message's own thread in the overlay (its ↗ opens it in Slack), and a card the connector cut short says so and links to the full thread.

The **Slack** page (in the sidebar when `slack.codex` is set, `?view=slack`) lists every thread the planning documents link, plus any opened from elsewhere. Favorites come first (threads you starred, and threads with a starred message), then the rest by last activity (the default) or by channel (`G`, kept in the URL as `group=channel`). Each row shows who started it and its opening line, its channel (when grouped by activity), **New replies** when it has messages since you last opened it in this browser, replies and people, the documents that cite it, and the age of its last message. A click on a cited task or plan, in a row, the inspector, or the thread overlay's **Linked from**, reads that document in a peek over the page instead of leaving it: links to other documents peek those, `Enter` or **Open** goes to the document, `Esc` returns to where you were, and ⌘-click opens the document directly. The same peek opens from planning-document links on the Issues page and its overview, the Activity inspector, and the PR and worktree overviews. Like every overlay, the peek keeps its document in the URL (`?peek=<path>`), so a refresh reopens it, Recently viewed and Favorites list it, and closing it offers **Reopen**. `F` filters across channels, people, text and citing documents; `J`/`K` move, `Enter` or a double click opens the thread overlay (a single click does on screens narrower than 1600px; wider ones select the newest thread and show its opening message and citing documents in an inspector). In an overlay opened from the page, `J`/`K` step to the next and previous thread in the list (its position shows in the header) and keep the page's selection in step. `S` or the row's star adds a thread to Favorites. Threads not read yet say so; `R` reads them all in the background through one connector session, four at a time (about a minute for 160 threads, no model), with progress in the toolbar, and reads every thread again when none are left. A plain click on a PR or commit link opens the in-app PR overview or commit diff (a commit's header names the PRs that carry it, each a button to that PR's overview, or else the branches that contain it), and a click on a Jira or Linear key opens the issue overview once that issue is synced (a Jira key outside `issues.jql` is read on its first click and kept in the cache as context: the overview opens at once with a spinner while it reads, and the link opens on Jira if that read fails); ⌘-, Ctrl- or Shift-click goes to the site. PR and issue links take their state color (green merged or done, red closed, muted draft). Hovering one shows a card with the source, state and age, the title, and, for an open PR, review, checks and conflicts, then author, stack position (the linked PR its base belongs to and the ones built on it), and diff size. Titles and states for GitHub (pull requests, issues and commits), Linear, Jira, and Slack come from `gh`, `acli`, the Linear key, and an optional `[slack] TOKEN` in `config.toml`, cached in the ignored `tmp/link-metadata.json`. Slack channel and direct-message names come from that token or from `reference/slack-channels.md`, one `- C…: #channel-name` or `- D…: @Person` line each; an unnamed DM shows its ID. The links panel is a single row of tabs, one per source after an All tab that lists every link grouped by source, over the list; while it is open, 1–9 pick a tab, ← → cycle through them, and ↑ ↓ move through the rows of the open tab (as they do in the Documents and Backlinks panels). The panel is as tall as its All list, up to most of the window, and keeps that height while you switch tabs. Below 600 px wide, only the selected tab shows its name. Each list has one row per linked item with the key or date, the title, and the state as colored text, each in a column shared by every row: links to an issue's comments fold into the issue's row, a commit cited by a longer or shorter hash appears once (by its first seven digits, titled with its commit message and dated), and a document's mentions of its own ID are left out. Documents without an ID lead with their title, starting in the key column, with the path underneath. Slack links group under their channel or DM. `npm run links` lists linked channels and DMs the file does not name yet.
