## Using the viewer

Run `../plan-viewer/cli.ts` in the workspace (the path to your checkout's `cli.ts`), then open `http://127.0.0.1:4173` (or the configured `port`). `plan-viewer serve` runs the server under `node --watch`, so it restarts itself when the viewer's own code changes (a pull, or an edit to a `*.ts` file); set `PLAN_VIEWER_WATCH=0` to run it without watching. When the viewer is out of date, a button appears in the bottom-right corner: **Update viewer · N new** when `origin` has commits the checkout lacks (it runs `git pull --ff-only` and restarts the server), **Restart viewer** when the checkout moved past what the server is running, and **Reload viewer** when the page is older than the server. The viewer fetches `origin` at most every five minutes and checks on load and every five minutes after; a pull that can't fast-forward shows git's error instead. `npm run dev:demo` in the viewer's repository runs the same `serve` against `examples/workspace/`. Edits to Markdown never restart it: they refresh the open page in place. A document opened from a link with a `#section` lands on that section once. On every page, a reload (the **Reload viewer** button, ⌘R, or Chrome bringing back a tab it discarded to save memory) and Back/Forward return to where you had scrolled, instead of jumping to the section or the top; a page whose data arrives late (Code, Issues) is scrolled there once it is tall enough, unless you scroll first. The viewer opens today's plan, presents milestones and Markdown sections as work cards, and can load a complete card plus commentary into a new Codex draft for review. The Tasks route lists unfinished repository tasks separately and opens each through the normal document reader and Codex draft flow. Task links in plans render current summary metadata from the authoritative task file. The rail's page links each show the one number worth knowing, amber when it needs you: documents changed today (Activity), due check-ins or else open tasks (Tasks), document counts (Reference), PRs awaiting your review or else your open PRs (Code), your issues in progress (Issues), and threads with new replies (Slack). Hovering or focusing a link shows a card with what sits behind it: the latest changed documents, check-ins then active and open tasks, review requests then your PRs with their review state, your issues by status, or the newest Slack threads. The pointer can move onto the card, and each row opens its item in an overlay over the page you're on (documents and tasks in the document peek, PRs, issues and Slack threads in their overviews); with the keyboard, `→` moves into the card, `↑`/`↓` move between rows, `Enter` opens one, and `←` or `Esc` goes back. Below the page links, the rail lists one row per day, newest first, with a hairline between weeks: each row says what the day was about, led by the plan's note for its first scheduled task (else that task's title, or the plan's first work heading for plans without tasks) and a count of the rest. Hovering a row shows the same kind of card: every scheduled task with its current status and the day's note for it, plus the day's other files, each opening in the document peek; clicking the row opens the plan, and `[` / `]` step to the previous or next day. Reference has its own list page; a folder under `reference/` groups its files under its README. The Activity route (`V`, first in the rail) is one list of everything, newest first and grouped by day: every task, daily plan and reference document by its file's modified time (with the sections and line counts an agent changed, when the server saw the edit), every `.draft` diagram by its source's save time (under **Diagrams**, with its task and subtitle; the inspector shows the drawing, and `Enter` or a click on it opens the diagram viewer), every in-scope Jira and Linear issue by its latest synced activity (a comment, a status change) or its `updated` time, every open PR in tracked repositories by GitHub's `updatedAt`, and, with `slack.codex` set, every synced Slack thread on the Slack page by its last message (its channel and citing documents as context, **New replies** when it changed since you last opened it, the inspector showing its opening message and citing documents, and `Enter` opening the thread overlay, where `J`/`K` walk the Slack rows on screen). Each row shows the time (the day header carries the date; hover for the full stamp and how long ago), a colored source icon, a key column that lines up every title (the item's own key in bold, such as `TASK-0163`, `#2236` or a Jira key, or in lighter type the task that holds it, for a task's asset, diagram or citing Slack thread), the item with what changed and where it sits (a task's project, an asset's task, an issue's parent, a PR's repository and branch), its state colored by meaning (green done or approved, blue in progress, amber waiting or needing review, red blocked or changes requested; PRs show their checks in a CI column of its own), and who owns it. Avatars are one picture per person across the viewer: `/api/people` joins GitHub commit authors (email, name, login), Linear users, Slack profiles (from a Slack token with `users:read` and `users:read.email`, or without one, from `slack.people` through Codex's Slack connector) and `people` in `config/viewer.json`, so a Jira assignee and the same person's PRs show the same photo (Slack's, else GitHub's, else Linear's). The index is cached in `tmp/people-cache.json` and rebuilt daily. The sticky toolbar filters by source (with counts), words (`F`), **Mine** (your issues and PRs, plus every document), and time: 24h, 7d (the default), 30d or All, or one day from the two-week strip of stacked bars beside it (each bar is labeled with its date, today in bold; click a bar, or `←`/`→` to step days; click it again to clear). Every filter and the selected row stay in the URL. On a wide screen a click selects a row and reads it in the inspector on the right: a document's status, last edit (the lines an agent added) and rendered text; an issue's Issues-page sidebar (owner, parent, planning documents, links, description, latest comments); a PR's review and CI state, reviewers, description, files and commits. `J`/`K` move, `Enter` or a double-click opens the item in full (the document, or the issue or PR overview, which walks the issues on screen with `J`/`K`), `O` opens it in a new tab, `Y` copies its link, and `Esc` clears the filters. The table stays at most 960px wide and the inspector takes the rest of the row, so on very wide monitors the space past them stays empty. Narrower than 1180px, a click opens the item in full. Issues and PRs re-read the server's caches every minute while the page is open. Document tables fit their columns to their content: short columns (names, dates, numbers) take exactly their one-line width, and the rest of the frame goes to the columns whose extra width shortens the table most, so prose columns get the room. Links and code under 28 characters never break; longer link titles wrap inside their cell. A table that cannot fit even at its narrowest keeps readable widths and scrolls sideways with its first column pinned. A table much taller than the window (over about 1.3 times 70% of its height) scrolls inside its frame under a sticky header, so the page can scroll past it. Its footer shows the rows in view ("Rows 13–24 of 158"), **Show all N rows** (and **Collapse**, which brings the table's top back into view) and **Expand**. The same two buttons sit in a tab on the table's top edge, always shown on a tall table. That tab is sticky below the document dock, so while you scroll through a table with every row shown, **Collapse** and **Expand** stay in view. Hovering a Markdown table shows **Copy** buttons (Markdown source, a real HTML table, as if selected and copied off the page, CSV, TSV for spreadsheets), **Download CSV** (named for the table's heading) and **Expand**, which opens the table in an overlay, titled with the heading above the table, with its columns fitted to their content, a sticky header and first column, and the same copy and download buttons. The overlay stays centered in the window. Drag any corner or edge to resize it; both sides move together, so the grip stays under the pointer. While dragging, a readout in the middle shows the size in pixels and as a share of the window, and the edges snap to ½, ⅔, the table's own size and the full window. **½ · ⅔ · Fit · Full** in the header (keys `1` to `4`) jump to those sizes, and double-clicking a grip fits the table. **Fit** sizes the overlay to the table (within the window), so a small table gets a small overlay, and ½, ⅔ and Full never make it taller than its rows need. **Fill width** (`F`, on unless you turn it off) spreads the columns across the overlay the way document tables fit their frame: short columns stay one line, prose columns share the rest and wrap, and header labels wrap too. It stays on through every resize, so the columns follow the overlay as you drag, until you size a column by hand. When the overlay is narrower than every column's longest word, the table takes its narrowest widths and scrolls sideways. The table sits 12px in from the overlay's edges. Sizes are kept as a share of the window, so one you dial in scales with the window, and the last one you chose is the size the next table opens at (Fit at first). A table on the document page puts itself in the URL (`table=2&table-size=60x70`, its place on the page and its size, plus `&table-fill=0` when Fill width is off), so a refresh, Recently viewed or a shared link reopens it as it was. In the expanded table, click a header to sort (again to reverse, a third time to clear; Shift-click adds a tiebreak, numbered in the header). Number, percentage and date columns sort by value, blanks always last, and numbers align right. The row under the headers filters each column: plain text matches anywhere (text columns suggest their values), `=x` matches exactly, `!x` excludes, and `> < >= <=` compare numbers, dates or text. **Filter all columns** (`/`) keeps rows that contain every word typed, and matches are highlighted. When nothing matches, the overlay says so, with **Clear filters**. Escape clears the focused filter before it closes the table, and **Clear** resets every filter and sort. Drag a header's right edge to resize a column; double-click it to fit the column to its content. Copy (except Markdown, which is always the source) and Download CSV take the rows showing, in their current order. A list item keeps the lines indented under it, such as a paragraph or a fenced code block, and a numbered list keeps counting across them and starts at its first number. `plan-viewer lint` reports a fence indented outside a list item, which renders as text, and a fence that is never closed. Fenced code blocks are syntax-highlighted in the same colors as Code view diffs: the fence's language picks the grammar (common languages and their aliases, such as `ts`, `py`, `sh`, `sql`, `yaml`), an unlabeled fence is colored only when one common language clearly fits, and `text` and tree fences stay plain. A `diff` fence keeps its red and green lines and changed-word marks, and the code in it is colored in the language the fence names after `diff` (` ```diff python `), or else the one its added and context lines most look like. Code blocks have the same space above and below; the hover tab sits in the space above. Hovering a fenced code block shows **Copy** (the verbatim source) and **Download** (named for its heading, with an extension from the fence's language). A `text` (or unlabeled) fence that holds a box-drawing tree, the **Feature scope** format of shape briefs (a root line, then `├── `/`└── ` branches under `│   ` rails), renders as an outline instead: guide lines connect each branch, a `Label: detail` item sets its label in bold, and wrapped lines indent under their item. Top-level branches in capitals (`PLANNED ADDITIONS: first release`, `EVALUATE BEFORE COMMITTING`, `LATER POSSIBILITIES`, `EXISTING`) become sections with a colored dot (blue planned, amber evaluate, gray later, green existing), the note after the colon, and a count of their leaf items; the root line totals them. A section with more than three items flows into two columns when the block is wider than 760px. **Text** in the hover tab shows the source fence instead; **Copy** and **Download** still copy the source. Any line that is not part of the tree keeps the fence as code. Each section heading has **Copy** beside **Open in**, which copies that section's Markdown, heading included.

Press `T` to return to today’s plan, `I` for Issues. Each document section's header has **Copy** (the section's Markdown under its heading), **Copy prompt** and **Open in Codex**. **Copy prompt** puts on the clipboard the prompt the agent draft would have opened with, for pasting into a chat that is already open instead of waiting for a new one. In every draft dialog it is a clipboard icon beside **Cancel** (sections, documents, selections, the global draft, next actions and work items), carrying whatever you typed, next to **Save note**, the default: `Enter` in a draft dialog keeps the same prompt as a note under Steps › **Up next** instead of opening anything (`⌘Enter`, or the **Open in Codex** button, opens the draft now), and in the Slack thread composer; with nothing typed, the prompt ends at the commentary heading, so the request you type after pasting lands under it. PR panels and overviews (on Code and in worktrees) have a **Copy** row under the agent row: the same skill icons, each copying that skill's prompt (the number keys still open the agent row's drafts). The issue inspector and overview list each issue skill by name with its number key, and a copy icon at the end of each line (on hover) copies that skill's prompt. One-click agent buttons also copy their prompt on `⌥`-click: PR review skills, PR note **Post as review** and **Work through**, a PR comment's discuss icon, issue skills, and worktree cleanup's **Agent review**. Initiatives keep their own copy icon. Press `C` while hovering over a work card, action or document section to open its Codex prompt (over either copy button too: `C` never copies); outside those targets, `C` opens a draft that names the open document (and its task ID for a task file), or carries no context only when no document is open, such as on Tasks or Code. With text selected in a document, `C` opens a draft for that file that quotes the selection and names the section it starts under (`Findings › c4574f89: …`), so the agent works on just that excerpt. `D` opens a draft for the current file, `[` / `]` open the previous / next day's plan, `P` / `N` step to the previous / next document of the open task (the task itself, then the other documents in its folder in the Documents panel's current sort, wrapping from the last back to the first; a `‹ 3 of 14 ›` stepper beside the breadcrumb does the same by click), `A` opens Tasks, `V` opens Activity, and `J` / `K` move to the next / previous document section. `⌘K` (or `Ctrl+K`) and `/` open document search in an overlay (`⌘K` works over the PR overview too, and opening a document from there closes the overview), with arrow keys to select a result and Enter to open it. Search matches titles, paths, task metadata, and each task's work breakdown items (Enter opens the task with that item's dialog) without filtering the sidebar. Matching is a little fuzzy: a word of four or more letters also matches when its letters appear in order in runs, so `sweepf` finds “sweep findings” before you know whether a space or dash comes next, and one mistyped letter in five is forgiven; matches as typed always rank above fuzzy ones, and fuzzy matches with fewer breaks rank higher. A query ranks every kind on one scale: an exact ID or key first, then the query in a title, then terms at the start of title words; live work (open or active tasks and items, open PRs, in-progress issues) rises, finished work sinks, recent edits rise, and yours rises. The eight best of any kind lead under **Top results**, and the rest follow grouped by kind (Tasks, Work items, Issues, Pull requests, Initiatives, Pages, Documents), kinds ordered by their best remaining match. A **Pages** group lists Today, Tasks, Reference, Plans, and each Code tab (Pull requests, Worktrees, Commits, Cleanup), so typing `pull` jumps straight to the PR list. **Local servers** (also in Pages) opens an overlay listing every local server the viewer started (`code.run`): its worktree, branch, URL, command, start time and live output, with Open (`Enter`), Restart (`R`), Stop (`S`, or Dismiss once it has exited) and the worktree overview (`W`). With no query, the palette leads with open PRs that need your review and your own open PRs. A PR number (`1938`, `#1938`, or `Orbit#27`) or words from a PR title, branch, or author list matching pull requests from tracked repositories, open or closed. A bare number is taken as an ID to open: the task (`0138` or `task-0138` is TASK-0138), PR (`#2270`) or issue key (`55734` is OPS-55734) it names exactly comes first, above work items and documents that only mention it; a leading zero means a task, so `0138` never matches PR #138. Enter opens the PR overview and `⌘Enter` opens the PR on GitHub. The highlighted PR is fetched in the background, so the overview usually opens instantly. `H` (or the clock button in the bottom-right corner) opens **Recently viewed** from anywhere, including over the PR overview: every page and PR or worktree overview this browser has shown: `↑`/`↓` and Enter, or `1`–`9`, go back to one and reopen its overview. A work item you opened is its own row (its ID and title, with the task beneath), so it reads apart from the task page; switching its Item/Graph view doesn't add another. A row under **You are here** names the list on screen, **Recently viewed** (where it opens) or **Recently changed** (documents edited outside the viewer), each with its count; `Tab` or a click anywhere on that row flips to the other, and `1`–`9` number the open list's rows. The filter covers both lists, so the counts show where the matches are, and an empty list says when the other one has some. It opens with focus in its filter, so typing narrows the list at once (so `H` then `snow` narrows to matching places, and `h` is just a letter there); Escape clears the filter, and a second Escape closes the menu. Closing an overview also shows a toast with **Reopen**. The star beside the breadcrumb above every page's title, and beside the close button in the PR, worktree, issue and initiative overviews, favorites whatever is open: a document, task, work item, page, PR, worktree, issue, or initiative. It's filled once favorited; click it again (or press `⌘D`/`Ctrl+D`, which works over the overviews too) to remove it. A favorite is keyed like Recently viewed, so a PR is one favorite whichever file was open. A toast confirms each change with **Undo**. **Favorites** at the top of the sidebar lists them, newest first, with the current one highlighted; clicking one reopens it as you left it (with its overview). Favorites live in this browser's local storage. Press `?` (`Shift+/`) or click **Keyboard shortcuts** for the full guide: one screen, grouped into Go to, Read, Find and keep, Agent drafts and General, with paired keys (`J` `K`, `N` `P`, `]` `[`) on one line and only this platform's modifier shown. Letter shortcuts pause in typing fields and open dialogs. Escape closes overlays; a Codex draft containing text stays protected until opened or explicitly canceled.

The viewer is local-only and dependency-free beyond Node.js and Codex Desktop on macOS. It watches authored Markdown under `daily/`, `tasks/` and `reference/` and refreshes the active document and library in place when those files change. A change never moves you: every other page (Tasks, Steps, Diagrams, Reference, Code, Plans, Issues, Slack, Activity) stays where it is and redraws in place, or keeps its own data. All viewer tabs share one live-update connection (one tab holds it and passes changes to the rest), so any number of tabs can stay open: a browser allows only six connections per host, and a connection per tab used to stall every request once six tabs were open. When a file changes from outside the viewer (an agent you handed work to, or your editor), a toast names the document, the sections the changed lines sit under, and how many lines came and went (`+3 −1`); **Open** (or **Show** for the document on screen) jumps to the first changed section. A burst of writes to one file updates its one toast. In the document itself, the lines an agent added or rewrote keep a light green tint until you open another document, and the first time they render (live, or from the toast) they and their sections flash once. Lines are found by their rendered text, so one that renders differently from its source, such as a task reference or a next action card, gets only the section flash. Recently viewed (`H`) lists the last eight changed documents under **Recently changed** (`Tab` from **Viewed**), and keeps them since the server started. Status changes made in the viewer itself don't toast. It omits folders listed under `exclude` in `config/viewer.json` (such as a generated issue corpus) from the document rail and live watcher. Opening a draft uses the native `codex://threads/new?prompt=…` handoff in the workspace's Codex project, but never submits it. Review or edit the prepared message in Codex Desktop and click Send there when it is ready. The server prints structured `codex-dispatch` logs for validation, draft opening, and failures. Press Enter in the viewer feedback field to open the draft; use Shift+Enter for a new line. Paste or drop images into a draft field to attach them: neither app's deep link carries attachments, so the server saves them to the workspace's ignored `tmp/handoff-images/` and the prompt lists their paths for the agent to open.

### Workspace layout

A workspace has four folders, one rule each:

- `daily/YYYY-MM-DD.md`: one plan per day.
- `tasks/TASK-NNNN/TASK-NNNN.md`: one task, with its documents, diagrams, images and `notes/` beside it in the same folder.
- `reference/`: prose that people and agents read. A folder per subject is fine; `reference/notes/` holds notes tied to no task.
- `config/`: what the tooling reads or writes: `viewer.json`, `code-repos.json`, `slack-channels.md`, `retired-tasks.md`, and other data files the workspace's scripts read.

The viewer, `lint`, `links` and `move` read only this layout. `plan-viewer migrate` moves a workspace from the older one (`tasks/TASK-NNNN.md` beside `tasks/TASK-NNNN-assets/`, `daily/YYYY/MM/DD/plan.md`, topics in `plans/`, a root `viewer.config.json`). Without `--write` it is a dry run: it prints every move and a **Fix first** list, each item with what to do, and exits 1 while that list has items, so an agent can fix and run it again. `--write` refuses until the list is empty and the git tree is clean, then moves the files (`git mv`), rewrites relative links, backticked paths and the path values in `config/viewer.json`, and lists the lines in `AGENTS.md`, `CLAUDE.md`, `package.json` and `scripts/` that still name the old layout. `lint` on an old-layout workspace reports only that it needs `migrate`. Old favorites and pasted `?path=` links break.

### Chat Threads

Open **Chat Threads** in the sidebar or through ⌘K. **Active** shows local Codex and Claude Code threads with a turn running or waiting for input. **Completed** shows up to 50 recent threads per app after their turns end, including interrupted Codex threads. Search by title, workspace, branch, app, model, agent role, or activity. On narrow screens, **Library** expands the navigation above the sessions. The full-width table lines up workspace, agent, model, usage, status and update time. The agent identifies the app and whether it ran on Desktop or CLI. The model and role appear when recorded. Filter counts show how many sessions are in each status or app before text search. Tokens shows the local Codex index’s reported thread total. Hover a count for the exact number. Touch devices show exact counts inline. From the search field, Down focuses the first openable conversation. Up and Down move between conversation links, and Enter opens one. Each usage bar compares its count with the largest reported total in the current results. Missing totals read **Unreported**. Choose **Most tokens** to rank reported usage, **Recent activity** for newest first, or **By workspace** to collect sessions sharing a working directory, with the most recently active group first. Search, sort, status and app filters survive reload. An empty filtered list offers **Clear search** or **Show all apps**. If a refresh fails, you can still filter the last results while the viewer retries. Click a thread's title to open its conversation in the desktop app. A standalone Claude CLI session becomes openable in Claude Desktop after the terminal process exits.

The viewer refreshes the list while the page is visible. It checks the local process and turn state, so a desktop window left open after a turn ends does not count as active. The list reads local session metadata on macOS and displays titles, workspaces, and activity times. Cloud and other machines' threads are outside this view.

### Setup

Open **Setup** in the sidebar or through ⌘K to see what the viewer can use and how it is configured.

- **Integrations** lists the GitHub CLI, Jira (`acli`), Linear, the Slack token, the Codex app server, draftably and the agent apps. The viewer checks each one when the page opens: a green dot works, a red dot is something your config uses that does not work, and a gray dot is not set up. Each row says what it turns on. **Recheck** runs the checks again.
- **Set up…** (or **Help…** on a working row) opens the note popover with a prompt for an agent: what is wrong, what it turns on, and the steps. Enter saves it as an Up next note, the quiet button drafts it in the agent app now, and the copy icon copies it. The prompt tells the agent to leave sign-ins and tokens to you; the viewer never shows a token.
- **Config files** lists the files in `config/` (not in the library, so this is where to read them), the repo list `code.reposFile` names, and `config.toml`. Each row says what reads the file. **View** shows a file read-only; **Edit…** or **Create…** drafts the change for an agent. `config.toml` holds tokens, so the page shows only whether it exists.
- **Prompts** starts with three routines, each with **Start…**, which fills it in for today and opens the note popover (Enter saves it to Up next; the quiet button opens it in the agent app). **Daily plan** writes `daily/<today>.md` from the last plan, Up next, the Steps priority, due check-ins and reviews waiting on you, then asks you to confirm the order. **Daily review** recaps the day against the plan, lists stale and waiting work, groups open agent flags into proposed fixes, and drafts tomorrow's plan. **Up next sweep** works the Up next queue in priority order and reports what waits on you. Like every prompt, each one is a file you can **Edit…**.
- Below the routines, **Prompts** lists every prompt the viewer sends to an agent: the handoffs from cards, documents, the composer, diagrams, Next actions and steps; PR notes, worktree cleanup, initiative Update and Retire, and Slack Discuss; plus the issue and PR skills from your settings. **View** shows the text with its `{slots}` marked (the viewer fills them with the file, step or your comment) and, for a customized prompt, what changed from the default. **Edit…** copies the default into `config/prompts/<id>.md`, which then wins, and drafts the edit for an agent. **Reset** deletes the copy so the default applies again.
- **Settings** lists every key in `config/viewer.json`, grouped, with its value, whether the file sets it, and its meaning from [configuration.md](configuration.md). Text, number and on/off keys save when you change them (Enter or leaving the field), and **Reset** removes a key so its default applies. Lists, objects and commands have **Configure…**, which drafts the change for an agent. Keys marked **restart** take effect after a restart. Filter the table with the box above it.

### Tab briefs

An agent that opens a viewer tab for you can say why with `brief=<Markdown>` in the URL, beside whatever else the tab opens (`path`, `diagram`, `pr`, `issue`): for example `/?path=tasks%2FTASK-0101%2FTASK-0101.md&brief=…`, built with `encodeURIComponent`. The first line is the title; the lines after it are the body, usually the ask, the decision waiting, and links. It renders like a document, so task, PR and issue keys become links, and `[Next actions](#next-actions)` names a section of the document the tab opened on. The brief floats at the top centre of the page, above any overlay, so it never moves the page under you. Clicking a section link closes any overlay and scrolls to that section; clicking another document opens it. PR, commit, initiative, issue and Slack links, in the title as in the body, open their in-app overview like any other link; other web links open in a new tab. Only the controls that exist to leave go straight to the site: an overview's own title, the Open on GitHub / Open in Jira icon buttons, and a comment's timestamp. Inside a PR's description and comments, a bare `#N` or commit SHA links within that PR's repository, as on GitHub.

× hides the brief to a chip in the bottom-left corner that shows its title; clicking the chip opens it again. The brief belongs to the tab, not the URL: it leaves the URL once read (so favorites and Recently viewed stay clean) and stays in the tab's session storage, so it survives navigation and reloads, and a hidden brief stays hidden after a reload. A URL with a different brief replaces it and opens it.

## Code view

The Code route (`G`, `?view=code`, opening on Pull requests) is a control center for the repositories listed in `config/code-repos.json` (`code.reposFile`); add or drop one from the gear menu beside the refresh button. Summary tiles across the top (live today, uncommitted, review requested, my PRs with failing CI, open PRs, safe to remove) jump to the matching filter, and a 30-day activity strip filters worktrees to a day when clicked. Selecting a row opens a detail pane that starts with the same label/value grid and icon rows as the overview's left column (status, author, branch, size, reviewers, review skills, worktree actions; for a worktree its path, ahead/behind, history, PR and cleanup reason), then commits, changed files, and ignored hand-made files. The expand icon beside the title opens the overview. `J`/`K` or the arrow keys move, `Enter` or a double-click opens the overview for a worktree or PR (or a commit's diff), `E` opens the worktree in the configured editor (`code.editor`, VS Code by default), `X` opens the configured terminal (`code.terminal`), `L` starts or stops the local server (`code.run`), `S` starts a new agent session, `Y` copies the path or link, `1`–`N` draft a configured review skill, and the key after them drafts an open **Discuss** prompt about the PR for you to finish, `F` focuses the filter, and `R` rescans everything, like the refresh icon.

- **Worktrees** lists every worktree newest first, by the latest of its creation, last commit, and uncommitted edits, with a recency dot, ahead/behind counts against main, PR and CI state, and icons for the editor, terminal, Finder, a new agent session, and the branch on GitHub. The panel stops at the bottom of the window and its list scrolls. Drafts wait for you to press Enter; Claude asks once to trust a folder opened this way.

Below sit **Linked**, the planning documents (tasks first) that name the PR the way documents link it (its GitHub URL, `<repo>#N`, or a bare `#N` in `github.defaultRepo`) or name a tracker key from its title or branch (`MOD-123`, `alex/mod-123-fix`), each read in a document peek over the overlay (`Enter` there opens it in full); then notes, each commit to walk (`N`/`P`), and the stack (click any row); then the changed files and the diff. The view toggle (**Description**, **Changes**, **Stack**; in a worktree **Local**, **Changes**, **Uncommitted**) sits in the header above the diff it switches, beside **One file / All files** and **Split / Unified**; the keyboard icon there lists every shortcut on hover. A PR or stack in a tracked repository is read from its local clone: its head and base commits are fetched by SHA only when missing (no branch or ref changes), and the diff, whole files and line counts all come from git, so even PRs over GitHub's 300-file or 20,000-line diff limit load. Other repositories use GitHub. **One file** steps through files with `J`/`K`; **All files** (`V` toggles) stacks every file in one scroll, rendering each as it nears view and holding files over 1,500 changed lines behind a click. **Viewed** checkboxes work like GitHub's: `X` marks the current file viewed and moves to the next unviewed one (wrapping to the top of the list), the header counts progress, viewed files collapse in **All files**, and a file that changes afterwards comes back unviewed with an amber ● in the file list (hover the Viewed box or the dot for when you checked it; stored per browser). The **Moved** row lists renames bundled by folder (`docs/ → client/ 13`); hovering one, or a renamed tile, outlines its old and new folders and fades the rest, and clicking pins it. **Edges** (`E`) adds a ribbon per move. Hover a tile for its old path, status and line counts; click it to open its diff; click a folder label or breadcrumb to zoom (`Backspace` zooms out). Expand (`F`) lifts the map over the whole overview in a frame you can resize from its bottom-right corner, so **Copy image** captures the shape you choose; `F` or `Esc` shrinks it back. Where the browser blocks image copying, the PNG downloads instead. In a stacked PR, `[` and `]` move to the PR below and above in the stack. **Stack** (beside Changes) shows one diff for the entire stack, from the bottom PR's base branch to the top PR's branch; notes stay per PR, so they can't be added there. The description renders GitHub's raw `<img>` and `<details>` tags; images attached to the PR are fetched once through `gh` (signed in) into the workspace's ignored `tmp/github-images/` and served from there. The PR overview opens on the Description; while it stays open, moving to another PR (`[`/`]`, a stack row, a linked PR) keeps the view you picked (a commit becomes Changes), and closing it resets the next open to the Description. On a PR, `D` always opens the Description; in a worktree it cycles Local, Changes and Uncommitted. Under the description sit the PR's comments, oldest first: conversation comments, line comments (file and line, full path on hover) and review summaries, skipping bare approvals. Bot comments (CI, Copilot, linkbacks) are hidden behind **Show N bot comments**. Each comment's discuss icon drafts a prompt in the configured agent app that quotes the comment, links it, and names the PR's worktree, ready for you to finish and send. Changed words inside a changed line or paragraph get a darker mark, and syntax colors come from both whole files (PR diffs included), so a docstring or comment that opens above a hunk stays shaded as one. Changed lines show their indentation and trailing whitespace as faint dots (spaces) and rules (tabs), and a change that only re-indents gets a lighter mark. On a PR, select code and press `C` (or click **Comment**), or click or drag down the line numbers, to keep a local note in `reference/pr-notes/` (`code.prNotesDir`; `Enter` saves, `Shift+Enter` adds a line); notes appear under the code they cover and in the PR column, where **Post as review** and **Work through** draft agent prompts over the draft notes. Each note keeps the code it quoted, so after new commits it follows that code: **moved to N** when the code shifted, **edited** when at least half of the quoted lines survive in one place (the note sits there), and **outdated** (red, counted in the Notes header) when the code is gone from the diff, which puts the note at the top of its file. The PR column lists each note in full, with a × on hover to delete it. Edited, outdated and file-changed notes count as stale: **Stale N** shows only those, and **Clear N stale** (click twice to confirm) deletes them all, clearing the way for a fresh round of review. Drag the PR column's right edge to widen it (double-click to reset; remembered per browser). The open PR is kept in the URL (`?pr=owner/repo#n`), with the current file (`&file=`) and commit or other scope (`&scope=`), so a refresh reopens the same view. `R` (or the refresh icon in the header) re-reads just this PR from GitHub, its details, checks, comments, diff and notes, and stays on the same file and view, without rescanning the Code page.

The left column uses the same grid: the path, ahead/behind, the branch's PR (click or `W` to open its overview), review skills, and the worktree actions. **Changes** is everything since the fork point, committed or not, plus new files, measured against the PR's base branch when the worktree has an open PR (so a stacked branch matches its PR) and against main otherwise. **Uncommitted** and each commit follow. **Local files** lists what no commit carries: untracked files and folders, and hand-made ignored files (dependency and build caches are left out), with size and age. Folders expand to their files; an untracked file opens in its diff, and an ignored one opens read-only in place (Markdown rendered, up to 2 MB). The URL keeps `?wt=<path>`. `R` re-reads just this worktree: its commits, files and diff.

Open PRs, PR history, and CI are cached in `tmp/code-cache.json`, so the Code page and ⌘K answer immediately after a restart. ## Plans

The Plans route (`M`, **Plans** in the sidebar, `?view=plans`) lists the initiatives on each tracked repository's `origin/main` (its remote default branch): every `initiative-map.json` outside hidden, dependency, build and vendor folders, with the Markdown files beside it. They are read straight from git, so the page shows main as of the last fetch. A PR that adds a new map adds its initiative too, read from the PR's head. The repo root's own changes since it split from main (uncommitted edits, new files and unpushed commits to a map or a Markdown file in an initiative folder) replace main's copy, tagged **uncommitted** or **unpushed**. Old `?view=code&tab=plans` links open this page.

The page works like the Code view: a toolbar on top, one dense table, and an inspector beside it on wide screens (1600px and up). The toolbar holds the filter (`/` or `F`; it matches titles, slugs, summaries, next actions, folders, repositories and PR numbers, `Esc` clears it, and `Enter` or `↓` moves into the table), the status scope with counts (**Open**, **Active**, **Paused**, **Planned**, **Finished** for completed and cancelled, **All**), **Group** (none, by repository with the most initiatives first, or by status), **Sort** (**Changed**, newest first; **Stage**, furthest along first; **Title**) and the rescan button (`R`). Each row has the status icon (dashed when inferred from the milestones; hover it for the status), the title with its next action under it, the repository (left out when grouped by repository), the **Stage** track, milestones done, when its folder last changed, and the open PRs that touch it. Each initiative folder is one row, even when its copies come from several places: the repo root's copy leads, then main's, then a PR's proposal. Tags after the title name every source (**proposed** for a PR that adds it, **uncommitted** or **unpushed** for the repo root), the PRs column lists every copy's PRs, and the inspector's Repo line names the other copies. The stage track has five segments, Intent › Shape › Plan › Build › Done: the three briefs fill once written (half for stale or draft), Build fills with the milestones, Done with a completed status, and the map's current phase is ringed; hover it for each stage's state. The filter, scope, group, sort and selected row stay in the URL (`&q=`, `&status=`, `&group=`, `&sort=`, `&sel=`). The sidebar's **Plans** link counts open initiatives, and its hover card lists the latest.

`J`/`K` (or the arrow keys) move the selection, and `Enter`, a double-click or a click on the title opens the reader. Without the inspector (on a laptop), a click on a row opens the reader at once. The inspector shows the summary, status, stage, next action, repository, folder (click to copy) and last change, the documents (each opens the reader at that document), milestones, open PRs, dependencies and the latest history, with **Update**, **Retire** and the copy icon in its header. `U`, `Shift+U` and `Y` work on the selected row too.

The reader is an overlay (`?plan=<repo>:<folder>&doc=<path>`) with the facts in its left column. Tabs pick the briefs and **Map** (the map's sections, milestones and full history); any other open file shows as its folder path beside them, and the left column lists every other file as a folder tree (folders fold; single-child chains read as one row). `J`/`K` walk the table in its current order (elsewhere, the open initiatives), `[`/`]` step through the documents, `M` opens the map, links to other Markdown files open in place with **Back** (`B`), and `Esc` closes it with the last initiative selected in the table. A brief's YAML front matter shows as one quiet line under its title. The reader never writes: `U` (or the pencil) drafts an **Update** prompt in Codex or Claude naming `code.planSkill`, the folder, map and open document, ending with a `---` line for your notes; `Shift+U` drafts **Retire** for a completed or cancelled initiative; the copy icon copies the update prompt instead. `Y` copies the folder path.

The same reader opens from anywhere else: ⌘K, Recently viewed, the sidebar's Plans hover card, and any GitHub link in a document to a file or folder inside an initiative (`github.com/<owner>/<repo>/blob/<branch>/docs/intent/<slug>/…`), which opens at that document. A modified click still goes to GitHub. Scans are cached by commit in the workspace's `tmp/plans-cache.json`, and open PRs with their changed files refresh every two minutes in the background.

## Issues

The Issues route (`I`, `?view=issues`) shows the Jira issues in `issues.jql`, the Linear teams in `issues.linear.teams`, and, with `issues.github`, the GitHub issues of the tracked repositories the way the Code page shows PRs: a dense list newest first, an inspector for the selected row, and a full-screen overview on `Enter` or a double-click (`?issue=KEY`), where the key at the top left links to the issue in its tracker, as a PR number does. It is read-only; every change goes through an editable agent draft. See [docs/issues-plan.md](docs/issues-plan.md) for the design.

- **All** lists open issues **By repo** (the default; a Jira project or Linear team counts as one) or **By update** (`&group=recent`), with type, priority, status, who reported it and who it is assigned to (the reporter's picture, an arrow, then the assignee; hover either picture for the name), the parent epic, the old key an issue was imported from ("was ATL-123"), and the PRs and worktrees that mention it. By repo, the most recently touched repository comes first, each header shows its open and closed counts, its latest update and a link to its issues on GitHub, a click on the header collapses it (remembered in the browser; `J`/`K` skip collapsed sections), rows show only the issue number, open issues sit above closed ones, and a line at the foot names the tracked repositories with nothing listed. A column that would be blank or identical on every row (priority for GitHub issues, people when no issue has a reporter or an assignee, status when every issue is open) is left out. Scope filters (Mine, Unassigned, In progress, Due in 7 days, With PRs) show only when they would narrow the list, and tabs with nothing in them (Triage, Epics) hide unless open; **Done** shows finished issues and **Bots** (when `issues.hideLabels` is set) shows machine-made ones. GitHub rows show labels and the comment count under the title. The toolbar says how many tracked repositories have issues in the list. Every row has a select box and, at its end, one sparkle button (shown on hover, on the selected row, or by keyboard) that opens a menu of the agent skills for that issue, headed by the issue it acts on, each skill by name with its number key and a copy icon for its prompt; in the open menu `↑`/`↓` move, `Enter` or the skill's number runs it, and `Esc` closes it and returns focus to the button; a repository header has a box that selects every issue shown in it (a dash when only some are) and the same menu for all of them. The **Code** column shows one PR (the newest open one) and a count of the rest; the inspector lists them all. The table always fits beside the inspector: long titles wrap, and the parent line under a title is cut short with an ellipsis. In a narrow window the Assignee column shows only the assignee's picture (hover for the name) and epic dates wrap, so no column is cut off. Tabs stay put while the filter or a person pick narrows them to zero. `Space` selects the current row and Shift-click selects a range. With a selection, the toolbar shows how many are picked and where, labeled draft buttons for all of them, and **Clear** (`Esc`). A draft about one GitHub repository's issues opens in that repository's checkout; a mix of repositories opens in `issues.workspace` or the planning workspace.
- **Triage** is the `issues.triage` queue. `Enter` opens the overview walking the queue: `J`/`K` move, `X` marks an issue seen at its current version and moves to the next unseen one (a later change in Jira brings it back), and seen issues hide until `U`. `Space` selects rows; with a selection, `1`–`N` draft one prompt about all of them.
- **Epics** groups epics under their initiatives, with a progress bar over every child (fetched by `parent`, whatever its component), confidence, dates, and owner. `→`/`←` or the chevron expand an epic's open children; issues outside the scope are dimmed.
- **Migration** (with both Jira and Linear configured) groups the same work across the two trackers. A Linear issue synced from Jira is a copy of it, a Jira issue labeled with a Linear key (`atl-123`) is an import of it, and with neither marker two open items with the same title are a likely match. Chains count as one group, so ATL-1 imported as OPS-2 and synced back as ATL-3 is one row. **In Linear only** lists open Linear issues and projects with no Jira counterpart, the work still to migrate. **Out of step** lists groups whose originals sit at different stages, **Open Linear copies** lists sync copies still open in Linear, **Same title** lists matches to confirm, and **Linked** holds the rest. Rows select for one bulk draft (a configured "migrate" skill, say).
- **Activity** is the feed of what changed: creations and comments from the start, then status, assignee, priority, parent, title, and label changes the viewer has observed since. Filter by Mine, Comments, or Status, or from a day (`&since=YYYY-MM-DD`).

The inspector and overview list **In planning**: every task and planning document that mentions the issue key (or a key it was imported under), bare or inside a tracker URL, tasks first. Clicking one closes the overview and opens the document; the Reopen toast brings the issue back.

Their **Code** list has one row per PR: checks, the number in its state's color (blue open, purple merged, struck-through closed), the title without the issue key it starts with, and the author. Open PRs come first, then merged, newest first within each; closed-unmerged PRs fold behind **Show N closed** when there are others, and the heading counts each state. Clicking anywhere on a row opens the PR overview. In descriptions and comments, Linear's mention tags (`<pull-request>`, `<issue>`, `<user>`, and the rest) render as links (a pull request goes to GitHub when its label names one), a run of two or more `Label: value` lines reads as a two-column facts grid, and a list item that is only a link shows its whole label, led by the PR's number, state and checks when it's one of the issue's PRs.

`A` picks assignees, `F` filters, `O` opens the issue in Jira, `Y` copies its link, `R` re-reads every issue, and in the overview `R` (or its refresh icon) re-reads just that Jira issue, `[`/`]` step through siblings, `P` opens the parent, and `W` opens a linked worktree. Clicking a PR opens the PR overview above the issue. ⌘K finds issues by key, by an old key, or by title words, and Recently viewed and the Reopen toast include issue overviews. Document links to an old key (`ATL-123`) show the state of the issue it became.

Linear issues read as issues (sub-issues under their parent) and Linear projects as epics, with the lead as owner, health as confidence, and the latest project update as the status update. A project's overview shows its summary and full body, custom status, priority, labels, initiatives, milestones with progress, resources, and comments. **Both / Jira / Linear** (`&source=`) picks which tracker the other tabs show. Linear keys are namespaced internally (`?issue=linear:ATL-12`) because a Jira project can reuse a Linear team's prefix. Linear copies of Jira issues only appear on the Migration tab, the inspector's **In the other tracker** lists every counterpart, and agent drafts name each counterpart as well. A person whose Linear account shows a handle gets the name their Jira account uses for the same email. Linear reads take about 40 seconds for 1,600 issues: in full hourly and on `R`, otherwise only issues updated since the last read.

With `issues.github` on, the GitHub issues of every repository the Code page tracks sit beside the others: a green open circle, or a purple checked one once closed (as **Done**), with `repo#12` as the key, the milestone in place of a component, and the first assignee as owner. **Mine** matches your `gh` login. Each sync reads every repository in full with `gh issue list --state all` (up to 500 issues each), so a deleted issue or a repository that left the tracked list drops out. PRs join a GitHub issue through the PRs that close it and through PR links in its body and comments. Keys are namespaced (`?issue=github:owner/repo#12`). With more than one source the toolbar gains an **All / Jira / Linear / GitHub** switch; the Migration tab needs both Jira and Linear.

Issues come from `acli`: a search lists the scope's keys, each issue is read with `acli jira workitem view KEY --fields '*all'`, and parents and epic children outside the scope are read as context. The copy lives in the workspace's ignored `tmp/issues-cache.json`. Every `issues.refreshMinutes` only the issues updated since the last sync are re-read, and the difference from the cached copy is the activity feed, because `acli` has no changelog. A full rescan runs hourly. The first sync of a few hundred issues takes about two minutes; afterwards the page answers from the cache. PRs join issues by key in their title or branch (through old keys too) and by GitHub links in the description and comments. Images uploaded to Linear are downloaded once with the Linear key into the ignored `tmp/linear-images/` and served from there.

The **Diagrams** page (sidebar, `?view=diagrams`) shows every `.draft` file under `daily/`, `tasks/` and `reference/` as cards big enough to read the drawing's labels: the diagram in its own proportions, then its title, subtitle, task ID and how long ago it was saved (hover for the exact time). **Group** arranges them by **Day** (the default: Today, Yesterday, weekday names, then dates), by **Task** (ID, title, status, project, count and last change, or the folder for diagrams outside a task) or by **Project**; groups and the diagrams inside them run newest first. **View** picks **Cards**, **Large** (two to a row, for reading detail) or **List** (a table with a small thumbnail, the file path, the task with its status, and when it was saved). A project is the `project:` line in a task's front matter (diagrams outside a task are "No project"); each card and list row names it unless the group does. The **Project** menu (shown when there is more than one, with counts) narrows the page to one project, and **Collapse all** / **Expand all** (or a click on the chevron or the group's title text, not the empty space beside it; in Task grouping the task ID is the link that opens the task) folds groups down to their headers, so Group by Task becomes a list of tasks with their diagram counts. The choices stay in the URL (`&by=task|project`, `&as=large|list`, `&project=`, `&fold=1`). `/` focuses the filter, which matches titles, subtitles, tasks and paths, marks the match, and stays in the URL (`&q=`); `Enter` opens the first match and `Esc` clears it. A card opens the diagram viewer with every diagram on the page in its rail. The viewer's rail lists each image as a small thumbnail with its title, under its task's heading on the Diagrams page; past 12 images it gets a filter (`Enter` shows the first match, `↑`/`↓` step through the matches, `Esc` clears it). The list refreshes when a `.draft` file is saved, added or removed.

Diagrams are [draftably](https://github.com/byronwall/draftably) `.draft` files kept beside the document (usually in the task's folder, `tasks/TASK-NNNN/`) and embedded like an image: `![What it shows](flow.draft)`. The server draws each one from its source with `draftably inspect --svg` (`diagrams.command`), so no PNG needs exporting and the picture never goes stale. A source that fails to compile draws its error in place of the picture. In the document a diagram is a small thumbnail with its title under it, and consecutive diagram lines (blank lines between them included) share one wrapping row. Clicking a thumbnail, or a plain link to a `.draft` file, opens it in the image viewer in diagram mode: the drawing on the left (wheel zoom that stays sharp at any size, drag to pan, the document's other images and diagrams in the rail) and its numbered, colored source on the right. Hovering a box marks its statement and its connections in both panes, and fades the rest of the drawing; hovering a statement marks what it draws; clicking a box scrolls the source to it. **Source** (`S`) hides or shows the source pane (remembered per browser; below 1600 px wide the pane starts hidden so the drawing gets the room, and a toggle there holds until the window crosses 1600 px again without changing what is remembered), **Copy** copies the source, **Copy PNG** (`C`) puts the drawing on the macOS clipboard as a 2× PNG that carries its source (`draftably extract` recovers the `.draft`; the server runs `draftably inspect --clipboard`, since a browser clipboard write would strip it); a diff diagram (`draftably compare` output, with `+ - ~` marks or a `compare` line) also gets **Inline**, **Side by side** and **Stacked** (`L` cycles them): Inline draws one merged drawing with its change marks (as if the file had no `compare` line), and the other two draw before and after panels in that arrangement, whatever the file's `compare` line says (the choice is remembered per browser and also applies to Copy PNG; with neither chosen, the file decides), and **Edit** (`E`) runs `draftably open` on the file, which opens the draftably editor in the browser. The box under the source (`D`) asks the agent app about the diagram: `Enter` saves the ask as an Up next note naming the `.draft` source and the task it sits in, `⌘Enter` (**Open in**) opens it as a draft now, and the clipboard icon copies it. What you type there stays with the diagram until it is sent, even if the viewer closes, and a backdrop click doesn't close the viewer while it holds text. Saving the `.draft`, from the editor or anywhere else, redraws every picture of it in every open tab at once, in place: embeds, the Diagrams page, the Activity inspector, the document dock, World views and the open viewer, source included; the viewer keeps its zoom, pan, source scroll and anything typed. Saving an image (`.png`, `.jpg`, `.gif`, `.webp`, `.svg`) under `daily/`, `tasks/` or `reference/` does the same for its pictures. Each picture's URL carries the file's modification time, so a view drawn later never shows an older copy the browser kept in memory. A live refresh of the document behind it (an agent editing the task) leaves the viewer open; only opening another document closes it. If the drawing or its source can't be loaded within 15 seconds, the source pane says so and offers **Retry**. The open diagram is kept in the URL (`?diagram=<path>`), so a refresh reopens it, and closing it offers Reopen. On a phone the source sits under the drawing.

A plain link to an image in the workspace (`[Proposal gallery](gallery.png)`) also gets a thumbnail like a diagram's. A list whose every item starts with an image link becomes a row of thumbnails: the link text is the caption, and the rest of the item (after an optional `:` or `—`) sits under it. Anywhere else, such as in a paragraph or a mixed list, the link stays in the text and the images it links to follow as a row of thumbnails. A thumbnail or the link opens the image viewer, with the document's other images and diagrams in its rail.

## Steps and the Outbox

The Steps page (sidebar, `?view=steps`) lists every open step of every unfinished task, highest priority first (see Priority below), filtered by **Next move**: **You decide** (approvals, decisions and choices), **You act · friction** (something only you can do; the group header lists, once each, the fixes that would remove it), **Agent**, and **Others**, with **Blocked** (prerequisites not done) and **Needs a kind** behind a toggle in the All view. Step titles in lists read as plain text: a Markdown link shows its label (a file name without its folder or `.md`), and a parenthetical that is only a link is left out; the inspector's heading keeps the real links. A step is a work-breakdown line; a leaf step, or a choice. It may end in `{kind, size}`:

```markdown
- W2.1: Comment on ABC-123 [open] (after: W1) {jira-comment, S}
- W3: How the fix lands [open] {pick-one, S}
  - W3.1: On main first — ships now [open] {option, recommended}
  - W3.2: Stacked on the other PR — one review, but waits [open] {option}
```

Kinds are `agent`, `check-in`, `decision`, `byron` (only you can do it), an outbound kind, or a choice: `pick-one`, `pick-any` (options as children, each `{option}` with a ` — trade-off`, one `recommended`) and `do-all` (an ordinary group). Sizes are `S`, `M` and `L`. Without a kind, a step takes its outbound draft's kind (a task asset whose front matter has `step: TASK-0101 W2.1`), else `agent` when a Next action names it, else `check-in` when it is waiting with a prompt. `waiting` means waiting on someone else. An outbound step is **You decide** while its draft is ready, **You act** when it is `send: manual`, and leaves the list once sent or dropped.

**Priority.** Every step gets a score from 0 to 99, and every list of steps (the Steps page, today's plan, the World's Today column, `plan-viewer next`) is sorted by it, with **Up next** steps pinned above all. The score adds: the task's `priority:` front matter (`p1` +30, `p2` the default 0, `p3` −20); +25 when today's plan names the step (`TASK-0140 W3.2`, or a `W1.2` later on a line that names its task) or +8 when it only names the task; up to about +35 for what finishing the step unblocks (`10 × log2(1 + n)`, where `n` counts the open steps whose `after:` names it or one of its scope parents, followed transitively); +10 when the next move is yours, since you hold everyone else up; +10 for `S`, +4 for `M` or no size, 0 for `L`; and a point a day of age, up to 14. Each row shows the score with a thin bar. Hovering the score (or focusing its row with the keyboard) opens a waterfall of where it comes from: one row per part (base, task priority, today's plan, unblocks with the names of the steps it unblocks, waits on you, size, age) with its signed points and a bar stepping from the running total before it to the one after, then the total. Rows of 70 and up are in the accent with a heavier title, and rows under 50 recede to gray, so the most important step is the first one read. The Steps page's **Sort** menu switches to **Unblocks most**, **Smallest first** or **Oldest first** (`&sort=`), and its **Group** menu groups the table by **Task**, **Next move**, **Kind** or **Status** (`&group=`; the last choice is remembered in this browser). A task group's header names the task, its step count and top score, and carries the task's **P1 · P2 · P3**; groups follow their highest-ranked step.

The Steps table edits in place, without selecting a row: the checkbox marks a step done (with a dated update), the dot puts it on or takes it off Up next, the **Kind**, **Size** and **Status** cells are menus, and double-clicking a title (or <kbd>F2</kbd> on a focused row) edits it, <kbd>Enter</kbd> or leaving the field to save and <kbd>Esc</kbd> to cancel. Each edit rewrites only that step's line in its task file. Nothing is selected when the page opens, so the table has the full width; clicking a row (or <kbd>Enter</kbd> on it) opens the inspector beside it, and **×** or <kbd>Esc</kbd> closes it. When the inspector narrows the table, the Task, Move and Age columns step aside so the editable ones stay in view; below the inspector's width a row opens the step dialog instead. The inspector's **P1 · P2 · P3** control sets the whole task's `priority:` (P2 removes the line).

Today's plan opens with a **Steps** panel: a thin **Up next | You | Agent | Others | All** toggle with counts (You by default; the choice stays in the URL as `&move=`), then the first eight of those steps by priority, one line each with the score (hover for its waterfall), a state pill (**Decide**, **Friction**, **Agent**, **Waiting**), the full title, and the task and step ID on the right. The panel is always as tall as its fullest segment, so switching never moves the page. A row opens the step dialog over the plan; **All N on Steps →** goes to the Steps page. `plan-viewer lint` checks steps too: kinds must be known, a `[waiting]` step can't be one that waits on you (`decision`, `byron` or a choice), a choice needs two or more `{option}` children with exactly one `recommended` until it is decided, open steps of tasks created on or after `steps.requireSizeFrom` need a size, step titles of tasks created on or after `steps.groundReferencesFrom` give each reference (`ABC-123`, `#12`, `repo#12`, `W1.2`, `repo@sha`) at least two words saying what it is, so a step reads on its own (`Merge #1954` fails, `Merge #1954, the streamed-chunk fix` passes), no prompt may contain a `steps.forbiddenInPrompts` word, and an outbound draft's `step` must exist in its own task and agree with it (a sent draft's step completed, a completed step's draft sent or dropped), and a `pr-comment` or `review-request` target must be a PR the sender can parse (`#2233`, `PyRel#3929`, or a `https://github.com/<owner>/<repo>/pull/<n>` URL).

The inspector's actions remove what would otherwise be friction. **Start** on an agent step opens the note popover (see **Launch buttons save notes** below); its **Start agent now** button runs `steps.start` as a local agent session with the step's prompt (or its title and task when it has none), marks the step `active`, and holds one of `steps.slots` slots until the run ends; with `steps.refill`, a finished run starts the next ready agent step that has a prompt. Only runs started here count toward the slots, and a step whose status is `active` without one shows **Agent · in progress**. A `byron` step's machinery file (front matter `kind: byron`, `step`, `run`, `target`, `undo`, `why`, `fix`) shows the statement: a single read-only statement gets **Approve and run**, which runs `steps.run`, appends the output to the file, and completes the step; anything that changes data gets only **Copy statement** and **Mark done**, since the viewer never runs it. A machinery file with `apply:` (an allow rule for Claude Code) gets **Apply**, which adds the rule once to `steps.settingsFile`, inside the workspace. A `decision` without a choice gets **Decide…** (a note; see Up next below) and **Mark decided**.

**Up next** queues a step for an orchestrating agent thread rather than starting a run of its own. Every step's actions (the inspector and the step dialog) carry an **Up next** toggle that adds `next` to the line's suffix (`- W2: Build it [open] {agent, M, next}`) or takes it off; agents can write the flag the same way. Flagged steps sort first (above any score), show a blue dot beside their title, and have their own **Up next** segment on the Steps page (`&move=next`), which includes blocked ones. Notes join the queue too. **Save note** in the composer (the default for <kbd>Enter</kbd>; <kbd>⌘</kbd><kbd>Enter</kbd> opens a draft instead) keeps the request instead of opening a draft: the full prompt the agent would have received (source file, task, selection, your words, pasted images) is written to `tasks/TASK-NNNN/notes/` when you were on a task, else `reference/notes/`, with `note: open` in its front matter. Relative links and image embeds in the copied selection are re-pointed from the source file's folder to the note's, so they still resolve. Open notes sit first under **Up next** as **Note** steps; **Mark done** sets `note: done` and adds a dated line. Every step's actions also have **Note…** (**Decide…** on a `decision` step): a small popover under the button, over whatever is open (the step dialog stays put), for a decision, an approval or direction in your own words. `Enter` saves it as a note tied to the step; `Esc` cancels, and a click outside closes it only while it is empty. The note is tied to the step (`step: TASK-0101 W2.1`). Its prompt has the agent read the step's task and any draft or machinery for it, record the note as a dated update, carry it through (a decision's step changes; an approved outbound draft sent as written or with the edits you asked for, plus the linking and cleanup around it; direction's work), and then set the step's status to what actually comes next. A note is not a completion: the step is completed only when the work finishes it or the note says so. While a note is open the step stays itself (same kind, status and actions) but waits on an agent: it shows as **Agent · notes to process** under Up next, and the inspector and step dialog list its notes under **Waiting for an agent**. **Approve and send** and **Mark decided** still act at once when there is nothing to add. `plan-viewer next` prints the flagged steps with who moves next, the task file and the prompt (`--json` for a script), so a thread told to "process what's next" reads that list, works each step or starts a session for it, and takes the flag off when the step is done.

**Launch buttons save notes.** Every button that would start an agent chat opens a small note popover under it instead: a PR's skill icons (Shakedown and the rest, on the list, the Stacks board, the PR and worktree overlays, and keys `1`–`4`), a PR's draft-note **Post as review** and **Work through** and a comment's discuss icon, **New session** (`S`, where the comment is required: it says what to do there), the Cleanup tab's **Agent review**, an issue's skills, an initiative's **Update** and **Retire** (`U`), and a step's **Start**. The comment box has focus; <kbd>Enter</kbd> saves the prompt the button would have sent, with your comment on top, as an open Up next note (a step's note is tied to its task and step; the rest go to `reference/notes/`), <kbd>Shift</kbd>+<kbd>Enter</kbd> adds a line, and <kbd>Esc</kbd> cancels and returns focus to the button. The old launch stays as the popover's quiet text button (<kbd>⌘</kbd><kbd>Enter</kbd>) and the clipboard icon copies the prompt; both carry your comment too (an initiative's lands under its `---` line); <kbd>⌥</kbd>-click on a skill icon still copies without opening anything. The composer, the diagram viewer's ask box, the Slack thread composer and the Stacks board's section moves work the same way: **Save note** is the filled button and <kbd>Enter</kbd>, the agent draft is secondary. **Approve and send** on an outbound draft is unchanged; it sends an approved message rather than starting a chat.

The segmented control filters by next move with counts, the menu by kind (**Outbound** is the Outbox, also in the sidebar), and the selection stays in the URL (`&select=TASK-0101:W2.1`). The inspector shows a choice's options with **Pick** (which completes the choice, defers the options not picked, and adds a dated update to the task), an outbound draft's approval panel, a step's prompt, or what a blocked step waits on. The sidebar counts the steps waiting on you.

**The step dialog** shows one step of any task over whatever page you are on; a step row anywhere opens it, and nothing behind it changes. Its top bar names the task (its status on hover; click the name to close the dialog and make the task the page) with its completed count, **Item | Graph** and **World** (the task's world). The rail on the left lists the task's steps under a small **You | Agent | All** toggle (You and Agent list only the steps waiting on that mover; All is the whole breakdown as a tree). The right pane reads top to bottom: a line with the step's ID, status and parent; the title; one row of actions under it, the step's own action first when it has one (**Mark decided**, **Start**, **Approve and run**, **Apply**), then **Note…**, **Up next**, **Send to agent** and a quiet **Update** (a draft that revises the item in the task file). Below that, a small facts grid: **Next move** (the state pill and, when it says more, why it is yours, the friction and its fix, or how to give an untyped step a kind), then **Waits on**, **Unblocks** and **Contains**, each item on its own row with its full title. Then sections that share one heading style and one hairline: a choice's options with **Pick** (its options aren't repeated under Contains), an outgoing draft with its approval panel and the text that will go out on a tinted surface, a statement or rule to run as a highlighted code block, the updates filed under it, its prompt rendered as Markdown on a pale blue surface, and where else the task mentions it (table rows read as their cells; the item's own Next actions line is left out, since the Prompt section names it). Empty sections are left out. ← and → step through the items with updates. `?step=TASK-0101:W2.1` reopens it on refresh, Recently viewed lists it, and closing it with Esc or × offers **Reopen**.

## Outbound drafts

A task asset that opens with `outbound:` front matter is a message, comment or issue waiting to go out:

```markdown
---
outbound: jira-comment
target: ABC-123
status: ready
step: TASK-0101 W2.1
send: comment
---

# Comment on ABC-123

Notes for the reader.

<!-- jira:start -->
The text that goes out.
<!-- jira:end -->
```

`outbound` is the kind (`jira-issue`, `jira-comment`, `jira-edit`, `jira-transition`, `it-ticket` (a RAI Help Desk request, filed by hand through the `create-it-ticket` skill in a Codex desktop app task), `slack`, `pr-comment`, `review-request`, `email`), `target` where it goes, `step` the work item it completes, and `send` the kind's flags for the workspace's sender (`manual` when you send it yourself). The text that goes out sits between `<!-- jira:start -->` and `<!-- jira:end -->`, or `<!-- send:start -->` and `<!-- send:end -->`; everything else is notes. `dry_run: true` makes every send of that file a dry run.

The draft's page opens with an approval panel: the kind, target, step, the hash of the text, a status, and the exact text under **Will go out** (the page below shows the notes). **Approve and send** records your click and that hash in the front matter (`status: approved`, `approved: <time> sha=<hash> by=viewer`) and runs `outbound.send`, which checks the hash again before sending; if the text changed since the page showed it, nothing is sent and the draft goes back to **Ready for you** with "Changed since you read it". A sender error leaves it **Didn't send** with the error and a **Retry**. **Send back** opens a box for your feedback, appends it under the notes as a dated section, sets `status: revise`, and starts `outbound.revise` (an agent that revises the draft and sets it back to `ready`, which needs your approval again). **Drop** sets `status: dropped`. With `steps.followUp`, a send (or **Mark sent**, **Mark done**, **Pick**, **Approve and run**, **Apply**) also saves an open **Follow through on W…** note tied to the step: the click does only the click, and the note asks an agent working Up next to reconcile the rest (the task's update and Next actions, steps that waited on it, trackers and threads it names, today's plan). Anything the draft lists under `## After it's sent` (or a machinery file under `## After it's done`) is copied into the note as items to do. A `send: manual` draft offers **Copy text** (as rich text) and **Mark sent** instead, with a note that it is friction. The viewer never sends anything itself; with no `outbound.send`, Approve and send is disabled.

## Tasks, next actions, and links

The Tasks page (`A`) lists unfinished tasks in sections, with a toolbar on top: **Filter** (`F`; Esc clears it, Enter or ↓ selects the first task) narrows the list by ID, title, summary, project, tags or status, and **Group** splits it by **Status** (the default: Check in, Active, Open, Waiting), **Project** (most tasks first), **Next move** (Waiting on you, With an agent, Waiting on others, No open steps), **Updated** (Today, This week, This month, Older) or **None**, each section headed with its count and sorted by the column you pick. Completed and deferred tasks always come after the live sections. `&q=` and `&group=` keep both on the URL. Each row has a **Steps** column counting each task's open steps by who moves next (`2 you`, `5 agent`, `1 waiting`, one per line, the part waiting on you in the waiting color; sorting by it puts the most waiting on you first) and a **Contents** column counting the documents, diagrams and images in each task's folder (sortable by their total); clicking a row reads it in the detail pane, whose **Steps** section shows the task's progress, the same counts, and the steps of the first mover with anything waiting (you first), each opening the step dialog over the page, with **All N open steps →** opening it on the whole list, and a double-click opens the task file. **Show N completed or deferred** adds the rest below them, in the same sort, and `&done=1` keeps that on the URL. It is the same control, wording, and rule as a task's work breakdown. **Waiting** is for work that sits with someone else: it stays tracked but drops below open tasks until it needs a look, then leads the list as **Check in** and counts on the rail's **Tasks** link. Two things bring it back, both computed, so nothing needs re-editing: its check-in date arriving, or something it watches moving. Pick **Waiting** in the status menu (click a status, or right-click a row) for a check-in a week out, or **3d**, **1w**, **2w** or **4w** under it; on a waiting task the same buttons push the date out. The viewer writes `check_in: YYYY-MM-DD` to the front matter (leaving waiting removes it); a waiting task without one checks in `checkInDays` after its `updated` date. It watches the PRs, GitHub issues and Linear or Jira issues its `## Next actions` name, and one counts as moved when its dated state (merged, closed, opened, or the tracker's last update, from the same cache as link titles) falls after the task's `updated` day, so recording a check-in or setting the status again resets it. The detail pane's **Waiting on** lists the check-in date and each watched item with its state, moved ones first and dated; the status's hover says why a task is due.

**World view** (the Tasks page's toolbar, the detail pane's **World**, a task page's dock, or `W`) lays work out by day, oldest at the left, so you can see what a task holds without clicking through it. A task's world has one column per day with activity (quiet stretches are skipped and marked with a dashed line; the columns share the window's width, so a short history spreads out and its thumbnails grow) and one lane each for work, diagrams, images, documents, updates, the daily plans that mention it, and other files in its `tasks/TASK-NNNN/` folder. The **Work** lane puts each completed work item on the day of the last update whose title names it (`… (W1.2)`; items no update names stay out), and a wider **Today** column holds the task's steps as the same list as today's plan (the **You | Agent | Others | All** toggle, You first when anything waits on you, eight a segment with **+N more** for the rest); each row, and each completed item on an earlier day, opens the step dialog above the world. Asset files sit on the day they last changed, and a picture exported beside its `.draft` (`flow.png` next to `flow.draft`) is left out, since the diagram stands for it. Diagrams and images show as small thumbnails, two to a column, that open the image viewer with the task's whole gallery. A day's cell shows six items of a kind: **+N more** under pictures opens the viewer at the first one left out, and under work, documents, updates or files it shows the rest in place (**Show less** folds them again), so one busy day can't stretch its whole lane; documents and plans open a peek, and an update opens the task in the peek at its Updates section, so closing either leaves you where you were; a file copies its path. The all-tasks world lists the Tasks page's tasks (same order, same completed toggle) one per row, each day marked with its newest picture and a dot per kind with its count (work, diagrams, images, documents, updates), and today's work dot counting what is ready; click a mark or a task to open that task's world at that day. **← All tasks** in a task's world (or Backspace, Alt+←, or the mouse's back button) returns to the all-tasks view at the same scroll and zoom, or opens it when you started on the task. **Open task** (or Enter) in a task's world closes every overlay and makes that task the page, however you got there; Back in the browser returns to where you started. Both open scrolled to the newest day at full size and fade days more than two weeks older than it. Drag to pan; pinch or ⌘-scroll zooms around the cursor; **Recent** and **All** reset the frame, and the zoom level resets to 100% when clicked. If the file list can't load, **Try again** sits beside the message. `?world=TASK-0082` (or `?world=all`, with `&world-day=` for the day) reopens it on refresh.

Each task's `## Next actions` contains short action headings and fenced `prompt` blocks. Write each prompt so an agent can advance one bounded step with the supplied repository context and a clear result to verify. An optional `Work item: W1.1` links it to the task's work breakdown. The viewer also gives existing bullet actions individual buttons.

Each action is one row: its work item, a status icon (a check when ready, a lock when it waits on prerequisites), the title, and the first line of its prompt. Click a row (its **Draft** hint shows on hover) to review the full prompt, add optional context, and click **Open in Codex** (or Claude, per the agent picker). Waiting actions open the same way: the row and the dialog say what they wait on (`After W1.2`), but nothing stops you, so you can tell the agent the prerequisite is done or that the action is still good context. The viewer uses the existing desktop handoff with a prepared, editable draft; review it and click Send there. The action prompt and absolute source file path are included. Additional context is optional; when given, it appears above the stored prompt and takes precedence where they differ. The server rechecks that the stored action hasn't changed before opening the draft. This local handoff expects an agent with access to the planning workspace.

A daily plan's **Scheduled tasks** section shows as one panel: a row per task bullet with its short number, its title, the plan's note for it in full (muted, with its PR, issue, task and Slack references as links; a click on a link follows it), and on the right its open steps counted by who moves next (`3 you · 5 agent · 1 waiting`, zeros left out). A waiting task says so in italics before its counts (`on hold, check in Nov 20`); a completed or deferred one shows only its status. A bullet that links several tasks before its note is one row for the first; the others lead its note as links. Clicking anywhere else on a row opens the step dialog on that task at its first step waiting on you, else its first ready step, with the rail on that mover. Other lines in the section render below the panel. A plan can also contain its own `## Next steps` action prompts for day-specific work; those still show, and they are what the dock's count covers. Task actions stay in their task files.

Use `## Work breakdown` to record the full known scope as nested bullets:

```markdown
- W1: Deliver the outcome [open]
  - W1.1: Reproduce the behavior [completed]
  - W1.2: Implement the fix [open] (after: W1.1)
  - W1.3: Verify the result [open] (after: W1.2)
```

IDs are unique within the task. Statuses are `open`, `active`, `waiting`, `deferred`, and `completed`. Nesting describes the scope; `after` describes prerequisites. A task page shows its work breakdown as one **Steps** panel in its place (its `## Next actions` section is not shown on such a page; the prompts there show in the step dialog). The panel has the same thin toggle as today's plan with this task's counts (**All** by default, so the whole open scope reads as an outline; `&move=` keeps another choice), then every step under a muted group header per workstream (a top-level item with steps under it, marked with a tree glyph instead of a status icon and with its progress on the right, a thin bar and `2 open · 3 done`, so it never reads as a step to act on; click it to read that item): its ID, status icon (a check when ready, a lock when it waits on prerequisites), a state pill only when it waits on you, the full title, and on the right a note count and `ready`, `after W1.2`, `active`, `running` or `waiting`. A step is a leaf, a choice, or an open item whose children are all done. Completed and deferred steps hide behind **Show N completed or deferred** at the bottom. **Graph** in the panel's header opens the dependency graph in a popover under it, with arrows from prerequisite to dependent and an expand control for a full-window view (clicking a node opens the step dialog); **World** opens the task's world. Clicking a row opens the step dialog over the page, and `C` over a row drafts that step for an agent. An update whose bold title names a work item, such as `- **2026-10-23 — Delete list (W2.3):** …` with nested bullets under it, is filed under that item, and its row and node show a note icon with the count. In the dialog, **Send to agent** opens a draft that advances the item (with its stored action prompt when it has one), and **Update with agent** opens one that revises the item in the task file (title, status, nesting, prerequisites, linked action) without doing the work. Both work on every item; when an open item is not ready **Send to agent** takes the waiting color, and the draft tells the agent what the item still waits on. **Item | Graph** in the dialog's top bar (or `G`) swaps the item pane for the task's whole dependency graph with the open item outlined, centered whole when it fits and on the open item when it does not; drag to pan (past the graph's edges, so any part can sit anywhere on screen) and scroll to zoom around the cursor, with the zoom kept as you move between items. The toolbar in the graph's corner has − and + (or the `-` and `=` keys), the zoom level, which resets to 100% when clicked (`0`), **Fit** to show the whole graph, never above 100% (`F`, or double-click the background), and **Item** to center the open item (`C`); clicking a node or a group's header reads that item, and the choice sticks across opens (`&graph=1`). Esc, ×, or a click outside it close the dialog, and backing out of a Send or Update draft returns to it; J and K walk the rail, ← → the nearest items with updates (from any item), and `&step=TASK-0101:W2.3` in the URL reopens it on refresh or from ⌘K (an older `&item=W2.3` on a task's page still opens it). Items that are completed or deferred, along with everything under them, are hidden from the Steps panel and graph until you check **Show N completed or deferred**; `&done=1` keeps that choice on the URL and carries it from document to document. Missing dependencies, duplicate IDs, and cycles produce warnings; readiness may be wrong until they are fixed, but actions still open.

Run `plan-viewer lint tasks/TASK-0001/TASK-0001.md` (in a workspace from `init`, `../plan-viewer/cli.ts lint …`) after authoring or updating a planning document, or `plan-viewer lint` to check the full authored corpus. It rejects invalid task front matter, work-breakdown warnings and action references to missing work items using the viewer's parsers. With `steps.groundReferencesFrom` set, every `.draft` diagram it is given or finds staged must also say what its references are: each title, subtitle, box, group, edge label and note needs two words per reference, so `RAI-55557\n#2278` fails and `RAI-55557 · role can't read data` passes. The same diagrams' headings (title, subtitle, group titles and legend entries) must not read as generated: lint rejects a heading that points at the drawing instead of saying something (`this diagram`, `Diagram 07 shows`, `08 and 09 show`), narrates its own layout (`up top`, `breaks below`, `the happy path first`), carries notes from the brief (`takeaway`, `at a glance`, `in my voice`, `here's`, `illustrates`), pads with filler (`key insights`, `comprehensive`, `seamless`, `robust`, `leverage`) or hedges (`potentially`, `arguably`, `essentially`). The patterns are narrow, so a data `row`, an `API key` or a product name passes; boxes and edge labels aren't voice-checked. Diagrams are checked only when named or staged, so a diagram gets grounded when someone touches it and older ones don't fail the full-corpus run. Point the workspace at the shipped pre-commit hook (`plan-viewer init` sets the workspace's `core.hooksPath` to it; see the README). The hook validates the staged contents of changed planning Markdown files, so a corrected working copy cannot hide an invalid staged version. Its link check also runs against the index, so files another session has not staged yet cannot block a commit. Valid work that is waiting on prerequisites passes lint. With `--staged` (the hook), lint also warns, without blocking the commit, when the commit piles work onto a task that was already `completed`: a new dated update, a step that isn't completed or deferred, or a new file in its folder (saved notes under `notes/` don't count). The `warn` line names the task and what was added, so the work can go to a new or live task instead. Completing the task in the same commit, reopening it (any other status) or retiring it (adding the `retired` tag) doesn't warn. The viewer itself never refuses to load over one bad task file: a task whose front matter doesn't parse (a placeholder an agent wrote to reserve its ID, say) is listed under Reference as **Invalid task** and opens as plain Markdown until it is fixed.

Tasks and daily plans can record related conversations under `## Chats` using ordinary labeled Markdown links. The viewer shows recorded chats above the document, in the selected task's detail pane, and alongside task references in daily plans. ChatGPT conversation links open in the browser; `codex://threads/<thread-id>` links open the existing chat in Codex Desktop, and Claude Desktop session links (`claude://claude.ai/epitaxy/local_<id>` or `claude://session/local_<id>`) open that session in Claude. Keep links in the authoritative task so daily plans pick them up without copying them. The viewer recognizes conversation links elsewhere in the prose too, while ignoring fenced prompts and inline code examples.

Viewer handoffs ask the receiving agent to record its verified conversation URL or thread ID when available, and the workspace's AGENTS.md can give agents the same convention. The new-draft handoff does not return a thread ID, so the viewer cannot automatically know the resulting conversation. An agent with trusted session identity can save it; otherwise paste the conversation's actual URL into `## Chats`. Shared snapshot URLs do not provide a place to send follow-up commentary and are not shown as related chats.

Documents get a clickable breadcrumb on its own line just above the title, left-aligned with the page content (task list, status, day, parent document, or copy target, then the copyable file path and the favorite star); list pages such as Tasks and Activity show only their count there. Documents also get a sticky bar with a Codex draft button and panels. **Work** (completed items as a ring and count) shows the task's Steps list in a panel that opens below the button and to its right (sliding left only as far as the window edge when there isn't room), and its **Work items** button opens the step dialog at the first ready item; a document with next actions but no work breakdown shows them as **Next actions** instead. **Updates** shows the same newest-first timeline in the dock and in the document. Write new entries as `- **2026-10-13 — Title:** What changed.` and indent continuation paragraphs and lists by two spaces. Older `### YYYY-MM-DD` headings and `- YYYY-MM-DD:` bullets can share the timeline with newer entries. Planning lint flags malformed date markers. Hover the relative date to see the exact day. **Diagrams** (when there are any) shows the diagrams the page embeds, then the task's other `.draft` files marked **Not embedded**, as thumbnails that open the diagram viewer. **Links** groups the outgoing links by source, and its last tab, **Linked from**, lists the documents that link here. A task with other files in `tasks/TASK-NNNN/` (and each of those files) gets a **Documents** panel: the task first, then its documents newest first under day headings, each with its `##` sections, when it was last edited (minutes or hours ago today, the time of day before that), its word count and images. **Edited**, **Created** and **Name** in the panel header re-sort it, and the choice is remembered in this browser; hover a row for its file name and exact edit and creation times. Standalone `TASK-0001` references, PRs (`#1810` in `github.defaultRepo`, `Orbit#2738` for a repository in `github.repos`), tracker keys such as `ATL-2845` (from `trackers`), slash lists such as `TASK-0016/0017` or `ATL-2733/2734`, commit SHAs (`Orbit@052702c8`, or bare SHAs inferred from the paragraph's PR references; not in headings, where a leading hex ID such as `### c4574f89: Connection dropped` names the section), 32-character trace IDs (through `traceUrl`), and Slack permalinks become icon links. Slack links open in the desktop app, or, with `slack.codex` set, in a thread overlay read once through Codex's Slack connector (a couple of seconds, no model) and then from the cache in `tmp/slack-threads.json`. The overlay reads like Slack: the channel name, who started the thread and when, the reply count and the people in it; day dividers; one header per run of messages from the same person within five minutes; emoji, skin tones and reactions (a workspace's custom emoji stay as `:name:`); mentions; and a **New since you last read** divider (`N`) from the last visit in this browser. The linked message is highlighted and scrolled to. **Linked from** lists the tasks and plans whose Slack links point into the thread, and each cited message carries the citing document's ID. **Links** (`L`) opens the documents' link browser over every link in the thread, with titles and states. Find (`F`) highlights matches and dims the other messages; `Enter` and `Shift+Enter` step through them. The box at the bottom (`D`) opens a Codex or Claude draft (whichever the agent picker chooses) in the planning workspace, with the thread saved to `tmp/slack-threads/<channel>-<ts>.md` for the agent to read and the citing documents named; typed text keeps the overlay open on `Esc` and backdrop clicks. `O` opens the thread in Slack (each message's ↗ opens that message), `R` reads it again (keeping your place), and `Esc` closes the overlay (or just the Links panel when it is open). The open thread is kept in the URL as `?slack=<permalink>`, so a refresh reopens it; closing it offers Reopen, and Recently viewed lists it by channel and first line. `⌘D` (or the header star) favorites the thread as opened, and each message's hover star favorites that message, which reopens the thread scrolled to it. Messages show their attached file names (open the message in Slack to see the files). A forwarded or shared message shows as a card under the message that shared it: its author, channel and date, and its text; a click on its header opens that message's own thread in the overlay (its ↗ opens it in Slack), and a card the connector cut short says so and links to the full thread.

The **Slack** page (in the sidebar when `slack.codex` is set, `?view=slack`) lists every thread the planning documents link, plus any opened from elsewhere. Favorites come first (threads you starred, and threads with a starred message), then the rest by last activity (the default) or by channel (`G`, kept in the URL as `group=channel`). Each row shows who started it and its opening line, its channel (when grouped by activity), **New replies** when it has messages since you last opened it in this browser, replies and people, the documents that cite it, and the age of its last message. A click on a cited task or plan, in a row, the inspector, or the thread overlay's **Linked from**, reads that document in a peek over the page instead of leaving it: links to other documents peek those, `Enter` or **Open** goes to the document, `Esc` returns to where you were, and ⌘-click opens the document directly. The same peek opens from planning-document links on the Issues page and its overview, the Activity inspector, and the PR and worktree overviews. Like every overlay, the peek keeps its document in the URL (`?peek=<path>`), so a refresh reopens it, Recently viewed and Favorites list it, and closing it offers **Reopen**. `F` filters across channels, people, text and citing documents; `J`/`K` move, `Enter` or a double click opens the thread overlay (a single click does on screens narrower than 1600px; wider ones select the newest thread and show its opening message and citing documents in an inspector). In an overlay opened from the page, `J`/`K` step to the next and previous thread in the list (its position shows in the header) and keep the page's selection in step. `S` or the row's star adds a thread to Favorites. Threads not read yet say so; `R` reads them all in the background through one connector session, four at a time (about a minute for 160 threads, no model), with progress in the toolbar, and reads every thread again when none are left. Anywhere in the viewer (documents, the brief, tables, inspectors, rail cards, waiting rows), a plain click on a PR or commit link opens the in-app PR overview or commit diff (a commit's header names the PRs that carry it, each a button to that PR's overview, or else the branches that contain it), and a click on a Jira or Linear key opens the issue overview once that issue is synced (a Jira key outside `issues.jql` is read on its first click and kept in the cache as context: the overview opens at once with a spinner while it reads, and the link opens on Jira if that read fails); ⌘-, Ctrl- or Shift-click goes to the site. PR and issue links take their state color (green merged or done, red closed, muted draft). Hovering one shows a card with the source, state and age, the title, and, for an open PR, review, checks and conflicts, then author, stack position (the linked PR its base belongs to and the ones built on it), and diff size. Titles and states for GitHub (pull requests, issues and commits), Linear, Jira, and Slack come from `gh`, `acli`, the Linear key, and an optional `[slack] TOKEN` in `config.toml`, cached in the ignored `tmp/link-metadata.json`. Slack channel and direct-message names come from that token or from `config/slack-channels.md`, one `- C…: #channel-name` or `- D…: @Person` line each; an unnamed DM shows its ID. The links panel is a single row of tabs, one per source after an All tab that lists every link grouped by source, over the list; while it is open, 1–9 pick a tab, ← → cycle through them, and ↑ ↓ move through the rows of the open tab (as they do in the Documents and Backlinks panels). The panel is as tall as its All list, up to most of the window, and keeps that height while you switch tabs. Below 600 px wide, only the selected tab shows its name. Each list has one row per linked item with the key or date, the title, and the state as colored text, each in a column shared by every row: links to an issue's comments fold into the issue's row, a commit cited by a longer or shorter hash appears once (by its first seven digits, titled with its commit message and dated), and a document's mentions of its own ID are left out. Documents without an ID lead with their title, starting in the key column, with the path underneath.
