## Using the viewer

Run `npm run viewer` in the workspace, then open `http://127.0.0.1:4173` (or the configured `port`). `plan-viewer serve` runs the server under `node --watch`, so it restarts itself when the viewer's own code changes (a pull, or an edit to a `*.ts` file); set `PLAN_VIEWER_WATCH=0` to run it without watching. When the viewer is out of date, a button appears in the bottom-right corner: **Update viewer · N new** when `origin` has commits the checkout lacks (it runs `git pull --ff-only` and restarts the server), **Restart viewer** when the checkout moved past what the server is running, and **Reload viewer** when the page is older than the server. The viewer fetches `origin` at most every five minutes and checks on load and every five minutes after; a pull that can't fast-forward shows git's error instead. `npm run demo` in the viewer's repository runs the same `serve` against `examples/workspace/`. Edits to Markdown never restart it: they refresh the open page in place. The viewer opens today's plan, presents milestones and Markdown sections as work cards, and can load a complete card plus commentary into a new Codex draft for review. The Tasks route lists unfinished repository tasks separately and opens each through the normal document reader and Codex draft flow. Task links in plans render current summary metadata from the authoritative task file. The Weeks route shows a five-week calendar where each day lists the tasks its plan scheduled (✓ when that day's done log mentions them), falls back to milestone headings for older plans, counts done outcomes and extra notes, and collapses empty weeks. Topics and Reference have their own list pages. The Activity route (`V`, first in the rail) is one list of everything, newest first and grouped by day: every task, daily file, topic and reference document by its file's modified time (with the sections and line counts an agent changed, when the server saw the edit), every in-scope Jira and Linear issue by its latest synced activity (a comment, a status change) or its `updated` time, and every open PR in tracked repositories by GitHub's `updatedAt`. Each row shows the time and age, a colored source icon, the item with what changed and where it sits (a task's project, an issue's parent, a PR's repository and branch), its state colored by meaning (green done or approved, blue in progress, amber waiting or needing review, red blocked or changes requested; PRs show their checks in a CI column of its own), and who owns it. Avatars are one picture per person across the viewer: `/api/people` joins GitHub commit authors (email, name, login), Linear users, Slack profiles (when a Slack token with `users:read` and `users:read.email` is set) and `people` in `viewer.config.json`, so a Jira assignee and the same person's PRs show the same photo (Slack's, else GitHub's, else Linear's). The index is cached in `tmp/people-cache.json` and rebuilt daily. The sticky toolbar filters by source (with counts), words (`F`), **Mine** (your issues and PRs, plus every document), and time: 24h, 7d (the default), 30d or All, or one day from the two-week strip of stacked bars beside it (each bar is labeled with its date, today in bold; click a bar, or `←`/`→` to step days; click it again to clear). Every filter and the selected row stay in the URL. On a wide screen a click selects a row and reads it in the inspector on the right: a document's status, last edit (the lines an agent added) and rendered text; an issue's Issues-page sidebar (owner, parent, planning documents, links, description, latest comments); a PR's review and CI state, reviewers, description, files and commits. `J`/`K` move, `Enter` or a double-click opens the item in full (the document, or the issue or PR overview, which walks the issues on screen with `J`/`K`), `O` opens it in a new tab, `Y` copies its link, and `Esc` clears the filters. The table stays at most 960px wide and the inspector takes the rest of the row, so on very wide monitors the space past them stays empty. Narrower than 1180px, a click opens the item in full. Issues and PRs re-read the server's caches every minute while the page is open. Hovering a Markdown table shows **Copy** buttons (Markdown source, a real HTML table, as if selected and copied off the page, CSV, TSV for spreadsheets), **Download CSV** (named for the table's heading) and **Expand**, which opens the table full-viewport with its columns fitted to their content, a sticky header and first column, and the same copy and download buttons. In the expanded table, click a header to sort (again to reverse, a third time to clear; Shift-click adds a tiebreak, numbered in the header). Number, percentage and date columns sort by value, blanks always last, and numbers align right. The row under the headers filters each column: plain text matches anywhere (text columns suggest their values), `=x` matches exactly, `!x` excludes, and `> < >= <=` compare numbers, dates or text. **Filter all columns** (`/`) keeps rows that contain every word typed, and matches are highlighted. Escape clears the focused filter before it closes the table, and **Clear** resets every filter and sort. Drag a header's right edge to resize a column; double-click it to fit the column to its content. Copy (except Markdown, which is always the source) and Download CSV take the rows showing, in their current order. A list item keeps the lines indented under it, such as a paragraph or a fenced code block, and a numbered list keeps counting across them and starts at its first number. `plan-viewer lint` reports a fence indented outside a list item, which renders as text, and a fence that is never closed. Hovering a fenced code block shows **Copy** (the verbatim source) and **Download** (named for its heading, with an extension from the fence's language). Each section heading has **Copy** beside **Open in**, which copies that section's Markdown, heading included.

Press `T` to return to today’s plan, `I` for Issues. Press `C` while hovering over a work card or action to open its Codex prompt; outside those targets, `C` opens a global draft. `D` opens a draft for the current file, `A` opens Tasks, `W` opens Weeks, `V` opens Activity, and `J` / `K` move to the next / previous document section. `⌘K` (or `Ctrl+K`) and `/` open document search in an overlay (`⌘K` works over the PR overview too, and opening a document from there closes the overview), with arrow keys to select a result and Enter to open it. Search matches titles, paths, task metadata, and each task's work breakdown items (Enter opens the task with that item's dialog) without filtering the sidebar. A query ranks every kind on one scale: an exact ID or key first, then the query in a title, then terms at the start of title words; live work (open or active tasks and items, open PRs, in-progress issues) rises, finished work sinks, recent edits rise, and yours rises. The eight best of any kind lead under **Top results**, and the rest follow grouped by kind (Tasks, Work items, Issues, Pull requests, Initiatives, Pages, Documents), kinds ordered by their best remaining match. A **Pages** group lists Today, Tasks, Weeks, Topics, Reference, and each Code tab (Pull requests, Worktrees, Commits, Plans, Cleanup), so typing `pull` jumps straight to the PR list. **Local servers** (also in Pages) opens an overlay listing every local server the viewer started (`code.run`): its worktree, branch, URL, command, start time and live output, with Open (`Enter`), Restart (`R`), Stop (`S`, or Dismiss once it has exited) and the worktree overview (`W`). With no query, the palette leads with open PRs that need your review and your own open PRs. A PR number (`1938`, `#1938`, or `Orbit#27`) or words from a PR title, branch, or author list matching pull requests from tracked repositories, open or closed. Enter opens the PR overview and `⌘Enter` opens the PR on GitHub. The highlighted PR is fetched in the background, so the overview usually opens instantly. `H` (or the clock button in the bottom-right corner) opens **Recently viewed** from anywhere, including over the PR overview: every page and PR or worktree overview this browser has shown: `↑`/`↓` and Enter, or `1`–`9`, go back to one and reopen its overview. A work item you opened is its own row (its ID and title, with the task beneath), so it reads apart from the task page; switching its Item/Graph view doesn't add another. A row under **You are here** names the list on screen, **Recently viewed** (where it opens) or **Recently changed** (documents edited outside the viewer), each with its count; `Tab` or a click anywhere on that row flips to the other, and `1`–`9` number the open list's rows. The filter covers both lists, so the counts show where the matches are, and an empty list says when the other one has some. It opens with focus in its filter, so typing narrows the list at once (so `H` then `snow` narrows to matching places, and `h` is just a letter there); Escape clears the filter, and a second Escape closes the menu. Closing an overview also shows a toast with **Reopen**. Press `?` (`Shift+/`) or click **Keyboard shortcuts** for the full guide. Letter shortcuts pause in typing fields and open dialogs. Escape closes overlays; a Codex draft containing text stays protected until opened or explicitly canceled.

The viewer is local-only and dependency-free beyond Node.js and Codex Desktop on macOS. It watches authored Markdown under `daily/`, `tasks/`, `plans/`, and `reference/` and refreshes the active document and library in place when those files change. When a file changes from outside the viewer (an agent you handed work to, or your editor), a toast names the document, the sections the changed lines sit under, and how many lines came and went (`+3 −1`); **Open** (or **Show** for the document on screen) jumps to the first changed section. A burst of writes to one file updates its one toast. In the document itself, the lines an agent added or rewrote keep a light green tint until you open another document, and the first time they render (live, or from the toast) they and their sections flash once. Lines are found by their rendered text, so one that renders differently from its source, such as a task reference or a next action card, gets only the section flash. Recently viewed (`H`) lists the last eight changed documents under **Recently changed** (`Tab` from **Viewed**), and keeps them since the server started. Status changes made in the viewer itself don't toast. It omits folders listed under `exclude` in `viewer.config.json` (such as a generated issue corpus) from the document rail and live watcher. Opening a draft uses the native `codex://threads/new?prompt=…` handoff in the workspace's Codex project, but never submits it. Review or edit the prepared message in Codex Desktop and click Send there when it is ready. The server prints structured `codex-dispatch` logs for validation, draft opening, and failures. Press Enter in the viewer feedback field to open the draft; use Shift+Enter for a new line. Paste or drop images into a draft field to attach them: neither app's deep link carries attachments, so the server saves them to the workspace's ignored `tmp/handoff-images/` and the prompt lists their paths for the agent to open.

## Code view

The Code route (`G`, `?view=code`, opening on Pull requests) is a control center for the repositories listed in `reference/code-repos.json` (`code.reposFile`); add or drop one from the gear menu beside the refresh button. Summary tiles across the top (live today, uncommitted, review requested, my PRs with failing CI, open PRs, safe to remove) jump to the matching filter, and a 30-day activity strip filters worktrees to a day when clicked. Selecting a row opens a detail pane that starts with the same label/value grid and icon rows as the overview's left column (status, author, branch, size, reviewers, review skills, worktree actions; for a worktree its path, ahead/behind, history, PR and cleanup reason), then commits, changed files, and ignored hand-made files. The expand icon beside the title opens the overview. `J`/`K` or the arrow keys move, `Enter` or a double-click opens the overview for a worktree or PR (or a commit's diff), `E` opens the worktree in the configured editor (`code.editor`, VS Code by default), `X` opens the configured terminal (`code.terminal`), `L` starts or stops the local server (`code.run`), `S` starts a new agent session, `Y` copies the path or link, `1`–`N` draft a configured review skill, and the key after them drafts an open **Discuss** prompt about the PR for you to finish, `F` focuses the filter, and `R` rescans everything, like the refresh icon.

- **Worktrees** lists every worktree newest first, by the latest of its creation, last commit, and uncommitted edits, with a recency dot, ahead/behind counts against main, PR and CI state, and icons for the editor, terminal, Finder, a new agent session, and the branch on GitHub. Under the branch sits its PR title, or else the head commit when it belongs to the row (a commit made on the branch, a detached HEAD, or the main checkout). A detached worktree is named by its short SHA (click to copy). **Folder** is one line: where the worktree sits (`main checkout`, a folder inside the repo such as `.claude`, a home folder such as `.codex`, `tmp`, or the folder beside the repo) and the segment that names it, left out when it only repeats the branch; a temp copy whose path embeds another worktree's path reads `↳ <that worktree>`. Click copies the full path, and the tip and detail pane show it. **Group** sorts into Changed (day, week, month), Repo, or Folder buckets, remembered per browser.
- **Pull requests** lists every open PR with CI, review decision, comments, labels, conflicts, size, and author. Filter by All / Review requested, author, drafts, or failing CI, and sort by updated, oldest, or largest. **Authors** (`A` on the Pull requests and Commits tabs, where it replaces the global Tasks shortcut) picks one or more people, you first and then by activity; clicking an avatar in a row filters to that person, and the pick follows you between the two tabs and stays in the URL (`&author=`). Every author shows the same mark in both tabs: their GitHub avatar over initials. With more than one tracked repository, every row on every tab starts with a two-letter repo mark on that repo's own hue (initials of its name, made unique). **Repos** (`G` on the Code page, where it replaces the global Code shortcut) is the legend: every tracked repository with its mark and how many rows it has on the current tab (repos with none sit below, under their own heading), and the place to filter to one or more of them, by mouse or with ↑↓, Enter, and Shift+Enter for only one; clicking a row's mark does the same, and the pick stays in the URL (`&repo=`). Worktree paths then drop the repo's own folder, since the mark already names it. Commits are matched to GitHub logins by noreply address, your own `user.email`, or by asking GitHub who wrote one of that email's commits, so a person with two git names is one author. The icons draft the review skills configured under `code.prSkills` in Codex or Claude Desktop (toggle at top right), in the PR's worktree when one exists and the main checkout otherwise. Drafts wait for you to press Enter; Claude asks once to trust a folder opened this way.
- **Plans** lists the initiatives on each tracked repository's `origin/main` (its remote default branch): every `initiative-map.json` outside hidden, dependency, build and vendor folders, with the Markdown files beside it. They are read straight from git, so worktrees and whatever branch a checkout is on don't matter, and the view shows main as of the last fetch (the inspector's **Repo** row says when that was). Each initiative is two lines: its status mark (planned, active, paused, completed, cancelled; dashed when the map records none and it is inferred from the milestones), title, and its next action on one line beneath (the inspector shows it in full, with the summary); then fixed columns for the **Stage** track, **Milestones** done out of total, **Deps** (↑ depends on, ↓ needed by, by slug within the repository), open **PRs** that touch the folder, and **Edited** (the newest commit to the folder). The stage track has five segments, Intent › Shape › Plan › Build › Done: the three briefs fill once written (half for stale or draft), Build fills with the milestones, Done with a completed status, and the map's current phase is ringed; hover it for each stage's state. A PR that adds a new map shows its initiative as a **proposed** row, read from the PR's head; a PR that deletes a map shows in red. **Open** (the default) hides completed and cancelled work; the other filters pick one status, **In open PRs** keeps only initiatives a PR touches, and **Group** sorts newest first into Edited buckets, repositories, stages, or statuses (remembered per browser). The inspector holds the full next action, the briefs in stage order with their recorded state, every other file as a folder tree (folders fold; single-child chains read as one row), the milestones, dependencies, PRs, and the latest history. `Enter` or a double-click opens the reader (`?plan=<repo>:<folder>&doc=<path>`): tabs for the briefs and **Map** (which lays out the map's sections, milestones, and full history), any other open file as its folder path beside them, and the same folder tree in the side column. `[`/`]` step through the documents, `M` opens the map, `J`/`K` walk the list, links to other Markdown files open in the reader with **Back** (`B`), and the outline marks the section you're reading. A brief's YAML front matter shows as one quiet line under its title. The view never writes: `U` (or the pencil beside the title) drafts an **Update** prompt in Codex or Claude naming `code.planSkill`, the folder, map and open document, ending with a `---` line for your notes; `Shift+U` drafts **Retire** for a completed or cancelled initiative; the copy icon copies the update prompt instead. `Y` copies the folder path. Scans are cached by commit in the workspace's `tmp/plans-cache.json`, and open PRs with their changed files refresh every two minutes in the background. ⌘K lists matching initiatives, and Recently viewed and the Reopen toast include the reader.
- **Cleanup** sorts worktrees into safe to remove (clean, with a merged or closed PR, a branch merged into main, or never used), review first (clean, no PR, idle two weeks), too new, and keep. "Skip if touched within" keeps worktrees created or touched in the last day or week out of the removable groups. Remove runs `git worktree remove` in small batches with a progress bar; it keeps branches and git refuses dirty trees. Agent review drafts a prompt that checks the selected worktrees first.

The **PR overview** (from ⌘K, `Enter` on a PR, or the expand icon in its detail pane) is a full-screen overlay. Its left column opens with one label/value grid: status (CI, review decision, conflicts), author, branch, size and labels, and reviewers (bots as an avatar only, every state named on hover), then one icon row of review skills (`1`…`9`) and one of worktree actions, led by the worktree overview (`W`). Every icon is named on hover. Below sit the view tabs (**Description**, **Changes**, **Stack**), notes, each commit to walk (`N`/`P`), and the stack (click any row); then the changed files and the diff. A PR in a tracked repository is diffed in its local clone (its head and base commits are fetched by SHA; no branch or ref changes), so even PRs over GitHub's 300-file or 20,000-line diff limit load; other PRs use GitHub's diff. **One file** steps through files with `J`/`K`; **All files** (`V` toggles) stacks every file in one scroll, rendering each as it nears view and holding files over 1,500 changed lines behind a click. **Viewed** checkboxes work like GitHub's: `X` marks the current file viewed and moves to the next unviewed one, the header counts progress, viewed files collapse in **All files**, and a file that changes afterwards comes back unviewed (stored per browser). Symbolic links get a `link` badge and show their target path instead of a one-line text diff. Lockfiles, snapshots, and vendored or minified files start collapsed; the chevron toggles any file. `/` filters the file list, and viewed files drop out of the list and `J`/`K` by default; `U` (or the count beside the filter) shows them again. Once every file is viewed the whole list returns, with "All N files viewed." under it. `S` switches split/unified. **Map** (beside the filter, or `T`) swaps the file list for a treemap of the change: folders as nested boxes, each file sized by its line count (from a local clone; lines changed otherwise) and filled from the bottom by its changed share in green and red, added files green, deletions hatched red, and each rename left as a hatched ghost at its old path. The **Moved** row lists renames bundled by folder (`docs/ → client/ 13`); hovering one, or a renamed tile, outlines its old and new folders and fades the rest, and clicking pins it. **Edges** (`E`) adds a ribbon per move. Hover a tile for its old path, status and line counts; click it to open its diff; click a folder label or breadcrumb to zoom (`Backspace` zooms out). The copy and download buttons export the map at the current zoom as a titled PNG, ready to paste into a PR. Expand (`F`) lifts the map over the whole overview in a frame you can resize from its bottom-right corner, so **Copy image** captures the shape you choose; `F` or `Esc` shrinks it back. Where the browser blocks image copying, the PNG downloads instead. In a stacked PR, `[` and `]` move to the PR below and above in the stack. **Stack** (beside Changes) shows one diff for the entire stack, from the bottom PR's base branch to the top PR's branch; notes stay per PR, so they can't be added there. The description renders GitHub's raw `<img>` and `<details>` tags; images attached to the PR are fetched once through `gh` (signed in) into the workspace's ignored `tmp/github-images/` and served from there. `D` cycles the views above the commits (Description and Changes, or Local, Changes and Uncommitted for a worktree), and `⇧D` jumps to a PR's description. Changed words inside a changed line or paragraph get a darker mark, and syntax colors come from both whole files (PR diffs included), so a docstring or comment that opens above a hunk stays shaded as one. Changed lines show their indentation and trailing whitespace as faint dots (spaces) and rules (tabs), and a change that only re-indents gets a lighter mark. On a PR, select code and press `C` (or click **Comment**), or click or drag down the line numbers, to keep a local note in `plans/pr-notes/` (`code.prNotesDir`); notes appear under the code they cover and in the PR column, where **Post as review** and **Work through** draft agent prompts over the draft notes. The open PR is kept in the URL (`?pr=owner/repo#n`), with the current file (`&file=`) and commit or other scope (`&scope=`), so a refresh reopens the same view.

The **worktree overview** (`Enter` on a worktree, **Open worktree overview**, or **Worktree overview** from a PR that has a local worktree) browses a worktree like a PR in the same overlay. The left column uses the same grid: the path, ahead/behind, the branch's PR (click or `W` to open its overview), review skills, and the worktree actions. **Changes** is everything since the fork point, committed or not, plus new files, measured against the PR's base branch when the worktree has an open PR (so a stacked branch matches its PR) and against main otherwise. **Uncommitted** and each commit follow. **Local files** lists what no commit carries: untracked files and folders, and hand-made ignored files (dependency and build caches are left out), with size and age. Folders expand to their files; an untracked file opens in its diff, and an ignored one opens read-only in place (Markdown rendered, up to 2 MB). The URL keeps `?wt=<path>`.

Dirty checks, CI, and PR history take about 15 seconds and load in the background; the refresh icon (or `R`) forces a rescan. Each PR's details and diff are cached on the server until the PR's updatedAt changes. Open PRs, PR history, and CI are cached in `tmp/code-cache.json`, so the Code page and ⌘K answer immediately after a restart. The server refreshes them every 10 minutes, and a request that finds the open-PR list more than a minute old returns the cached list and refreshes it in the background.

## Issues

The Issues route (`I`, `?view=issues`) shows the Jira issues in `issues.jql`, the Linear teams in `issues.linear.teams`, and, with `issues.github`, the GitHub issues of the tracked repositories the way the Code page shows PRs: a dense list newest first, an inspector for the selected row, and a full-screen overview on `Enter` or a double-click (`?issue=KEY`). It is read-only; every change goes through an editable agent draft. See [docs/issues-plan.md](docs/issues-plan.md) for the design.

- **All** lists open issues **By repo** (the default; a Jira project or Linear team counts as one) or **By update** (`&group=recent`), with type, priority, status, assignee, the parent epic, the old key an issue was imported from ("was ATL-123"), and the PRs and worktrees that mention it. By repo, the most recently touched repository comes first, each header shows its open and closed counts, its latest update and a link to its issues on GitHub, a click on the header collapses it (remembered in the browser; `J`/`K` skip collapsed sections), rows show only the issue number, open issues sit above closed ones, and a line at the foot names the tracked repositories with nothing listed. A column that would be blank or identical on every row (priority for GitHub issues, assignee when no one is assigned, status when every issue is open) is left out. Scope filters (Mine, Unassigned, In progress, Due in 7 days, With PRs) show only when they would narrow the list, and tabs with nothing in them (Triage, Epics) hide unless open; **Done** shows finished issues and **Bots** (when `issues.hideLabels` is set) shows machine-made ones. GitHub rows show labels and the comment count under the title. The toolbar says how many tracked repositories have issues in the list. Every row has a select box and a **Send to Codex** (or Claude) column with the agent drafts for that one issue; a repository header has a box that selects every issue shown in it (a dash when only some are) and drafts for all of them. `Space` selects the current row and Shift-click selects a range. With a selection, the toolbar shows how many are picked and where, labeled draft buttons for all of them, and **Clear** (`Esc`). A draft about one GitHub repository's issues opens in that repository's checkout; a mix of repositories opens in `issues.workspace` or the planning workspace.
- **Triage** is the `issues.triage` queue. `Enter` opens the overview walking the queue: `J`/`K` move, `X` marks an issue seen at its current version and moves to the next unseen one (a later change in Jira brings it back), and seen issues hide until `U`. `Space` selects rows; with a selection, `1`–`N` draft one prompt about all of them.
- **Epics** groups epics under their initiatives, with a progress bar over every child (fetched by `parent`, whatever its component), confidence, dates, and owner. `→`/`←` or the chevron expand an epic's open children; issues outside the scope are dimmed.
- **Migration** (with both Jira and Linear configured) groups the same work across the two trackers. A Linear issue synced from Jira is a copy of it, a Jira issue labeled with a Linear key (`atl-123`) is an import of it, and with neither marker two open items with the same title are a likely match. Chains count as one group, so ATL-1 imported as OPS-2 and synced back as ATL-3 is one row. **In Linear only** lists open Linear issues and projects with no Jira counterpart, the work still to migrate. **Out of step** lists groups whose originals sit at different stages, **Open Linear copies** lists sync copies still open in Linear, **Same title** lists matches to confirm, and **Linked** holds the rest. Rows select for one bulk draft (a configured "migrate" skill, say).
- **Activity** is the feed of what changed: creations and comments from the start, then status, assignee, priority, parent, title, and label changes the viewer has observed since. Filter by Mine, Comments, or Status, or from a day (`&since=YYYY-MM-DD`).

The inspector and overview list **In planning**: every task and planning document that mentions the issue key (or a key it was imported under), bare or inside a tracker URL, tasks first. Clicking one closes the overview and opens the document; the Reopen toast brings the issue back.

`A` picks assignees, `F` filters, `O` opens the issue in Jira, `Y` copies its link, `R` re-reads every issue, and in the overview `[`/`]` step through siblings, `P` opens the parent, and `W` opens a linked worktree. Clicking a PR opens the PR overview above the issue. ⌘K finds issues by key, by an old key, or by title words, and Recently viewed and the Reopen toast include issue overviews. Document links to an old key (`ATL-123`) show the state of the issue it became.

Linear issues read as issues (sub-issues under their parent) and Linear projects as epics, with the lead as owner, health as confidence, and the latest project update as the status update. A project's overview shows its summary and full body, custom status, priority, labels, initiatives, milestones with progress, resources, and comments. **Both / Jira / Linear** (`&source=`) picks which tracker the other tabs show. Linear keys are namespaced internally (`?issue=linear:ATL-12`) because a Jira project can reuse a Linear team's prefix. Linear copies of Jira issues only appear on the Migration tab, the inspector's **In the other tracker** lists every counterpart, and agent drafts name each counterpart as well. A person whose Linear account shows a handle gets the name their Jira account uses for the same email. Linear reads take about 40 seconds for 1,600 issues: in full hourly and on `R`, otherwise only issues updated since the last read.

With `issues.github` on, the GitHub issues of every repository the Code page tracks sit beside the others: a green open circle, or a purple checked one once closed (as **Done**), with `repo#12` as the key, the milestone in place of a component, and the first assignee as owner. **Mine** matches your `gh` login. Each sync reads every repository in full with `gh issue list --state all` (up to 500 issues each), so a deleted issue or a repository that left the tracked list drops out. PRs join a GitHub issue through the PRs that close it and through PR links in its body and comments. Keys are namespaced (`?issue=github:owner/repo#12`). With more than one source the toolbar gains an **All / Jira / Linear / GitHub** switch; the Migration tab needs both Jira and Linear.

Issues come from `acli`: a search lists the scope's keys, each issue is read with `acli jira workitem view KEY --fields '*all'`, and parents and epic children outside the scope are read as context. The copy lives in the workspace's ignored `tmp/issues-cache.json`. Every `issues.refreshMinutes` only the issues updated since the last sync are re-read, and the difference from the cached copy is the activity feed, because `acli` has no changelog. A full rescan runs hourly. The first sync of a few hundred issues takes about two minutes; afterwards the page answers from the cache. PRs join issues by key in their title or branch (through old keys too) and by GitHub links in the description and comments. Images uploaded to Linear are downloaded once with the Linear key into the ignored `tmp/linear-images/` and served from there.

## Tasks, next actions, and links

The Tasks page (`A`) lists unfinished tasks; **Show N completed or deferred** adds the rest below them, in the same sort, and `&done=1` keeps that on the URL. It is the same control, wording, and rule as a task's work breakdown.

Each task's `## Next actions` contains short action headings and fenced `prompt` blocks. Write each prompt so an agent can advance one bounded step with the supplied repository context and a clear result to verify. An optional `Work item: W1.1` links it to the task's work breakdown. The viewer also gives existing bullet actions individual buttons.

Each action is one row: its work item, a status icon (a check when ready, a lock when it waits on prerequisites), the title, and the first line of its prompt. Click a row (its **Draft** hint shows on hover) to review the full prompt, add optional context, and click **Open in Codex** (or Claude, per the agent picker). Waiting actions open the same way: the row and the dialog say what they wait on (`After W1.2`), but nothing stops you, so you can tell the agent the prerequisite is done or that the action is still good context. The viewer uses the existing desktop handoff with a prepared, editable draft; review it and click Send there. The action prompt and absolute source file path are included. Additional context is optional; when given, it appears above the stored prompt and takes precedence where they differ. The server rechecks that the stored action hasn't changed before opening the draft. This local handoff expects an agent with access to the planning workspace.

Daily plans show **Next steps** from tasks linked under **Scheduled tasks**, with one row per task (its number and title, linking to the task) above its first ready action, or its first action when none is ready; **+N more** opens the task's full list. Completed, waiting, and deferred tasks are omitted. A plan can also contain its own `## Next steps` action prompts for day-specific work. Task actions stay in their task files.

Use `## Work breakdown` to record the full known scope as nested bullets:

```markdown
- W1: Deliver the outcome [open]
  - W1.1: Reproduce the behavior [completed]
  - W1.2: Implement the fix [open] (after: W1.1)
  - W1.3: Verify the result [open] (after: W1.2)
```

IDs are unique within the task. Statuses are `open`, `active`, `waiting`, `deferred`, and `completed`. Nesting describes the scope; `after` describes prerequisites. The viewer shows the hierarchy and a scrollable graph with arrows from prerequisite to dependent. Each row's **After** list names its prerequisites, with completed ones in lighter text; on a row with an action, hovering swaps that list for the **Draft** hint. Any tree row or graph node with a linked action opens the same draft dialog, ready or not. Clicking any row or graph node opens the work item dialog; on a row with a linked action, **Draft** takes the place of its **After** list while you hover and opens that action directly. An update whose bold title names a work item, such as `- **2026-10-23 — Delete list (W2.3):** …` with nested bullets under it, is filed under that item, and its row and node show a note icon with the count. The dialog has the task (ID, title, status, completed work items) across the top, the whole breakdown as a rail on the left, and on the right the item's status and parent, what it waits on, unblocks and contains, its next action, the updates filed under it as dated notes, and **Also mentioned**: sentences elsewhere in the task (other updates, findings) that name it, each linking to its section. **Send to agent** opens a draft that advances the item (with its stored action prompt when it has one), and **Update with agent** opens one that revises the item in the task file (title, status, nesting, prerequisites, linked action) without doing the work. Both work on every item; when the item is not ready they turn yellow, and the draft tells the agent what the item still waits on. **Item | Graph** in the dialog's top bar (or `G`) swaps the item pane for the task's whole dependency graph with the open item outlined, centered whole when it fits and on the open item when it does not; drag to pan (past the graph's edges, so any part can sit anywhere on screen) and scroll to zoom around the cursor, with the zoom kept as you move between items. The toolbar in the graph's corner has − and + (or the `-` and `=` keys), the zoom level, which resets to 100% when clicked (`0`), **Fit** to show the whole graph, never above 100% (`F`, or double-click the background), and **Item** to center the open item (`C`); clicking a node or a group's header reads that item, and the choice sticks across opens (`&graph=1`). Only Esc or × close the dialog, and backing out of a Send or Update draft returns to it; J and K walk every item, ← → the nearest items with updates (from any item), and `&item=W2.3` in the URL reopens it on refresh or from ⌘K. Items that are completed or deferred, along with everything under them, are hidden from the tree and graph until you check **Show N completed or deferred**; `&done=1` keeps that choice on the URL and carries it from document to document. Missing dependencies, duplicate IDs, and cycles produce warnings; readiness may be wrong until they are fixed, but actions still open.

Run `npm run lint -- tasks/TASK-0001.md` after authoring or updating a planning document, or `npm run lint` to check the full authored corpus. It rejects invalid task front matter, work-breakdown warnings and action references to missing work items using the viewer's parsers. Point the workspace at the shipped pre-commit hook (see Quick start). The hook validates the staged contents of changed planning Markdown files, so a corrected working copy cannot hide an invalid staged version. Its link check also runs against the index, so files another session has not staged yet cannot block a commit. Valid work that is waiting on prerequisites passes lint.

Tasks and daily plans can record related conversations under `## Chats` using ordinary labeled Markdown links. The viewer shows recorded chats above the document, in the selected task's detail pane, and alongside task references in daily plans. ChatGPT conversation links open in the browser; `codex://threads/<thread-id>` links open the existing chat in Codex Desktop. Keep links in the authoritative task so daily plans pick them up without copying them. The viewer recognizes conversation links elsewhere in the prose too, while ignoring fenced prompts and inline code examples.

Viewer handoffs ask the receiving agent to record its verified conversation URL or thread ID when available, and the workspace's AGENTS.md can give agents the same convention. The new-draft handoff does not return a thread ID, so the viewer cannot automatically know the resulting conversation. An agent with trusted session identity can save it; otherwise paste the conversation's actual URL into `## Chats`. Shared snapshot URLs do not provide a place to send follow-up commentary and are not shown as related chats.

Documents get a clickable breadcrumb (task list, day switcher, parent document, or copy target) and a sticky bar with a Codex draft button, a **Work** button (completed items as a ring and count) that opens the work item dialog at the first ready item, and panels for next actions, updates, outgoing links grouped by source, and backlinks. Standalone `TASK-0001` references, PRs (`#1810` in `github.defaultRepo`, `Orbit#2738` for a repository in `github.repos`), tracker keys such as `ATL-2845` (from `trackers`), slash lists such as `TASK-0016/0017` or `ATL-2733/2734`, commit SHAs (`Orbit@052702c8`, or bare SHAs inferred from the paragraph's PR references), and Slack permalinks become icon links; Slack links open in the desktop app. A plain click on a PR or commit link opens the in-app PR overview or commit diff (a commit's header names the PRs that carry it, each a button to that PR's overview, or else the branches that contain it), and a click on a Jira or Linear key opens the issue overview once that issue is synced; ⌘-, Ctrl- or Shift-click goes to the site. PR and issue links take their state color (green merged or done, red closed, muted draft). Hovering one shows a card with the source, state and age, the title, and, for an open PR, review, checks and conflicts, then author, stack position (the linked PR its base belongs to and the ones built on it), and diff size. Titles and states for GitHub, Linear, Jira, and Slack come from `gh`, `acli`, the Linear key, and an optional `[slack] TOKEN` in `config.toml`, cached in the ignored `tmp/link-metadata.json`. Slack channel and direct-message names come from that token or from `reference/slack-channels.md`, one `- C…: #channel-name` or `- D…: @Person` line each; an unnamed DM shows its ID. The links panel is a single row of tabs, one per source after an All tab that lists every link grouped by source, over the list; while it is open, 1–9 pick a tab and ← → cycle through them. Each list has one row per link with the key or date, the title, and the state as colored text, each in a column shared by every row; documents without an ID lead with their title, with the path underneath. Slack links group under their channel or DM. `npm run links` lists linked channels and DMs the file does not name yet. Run `npm run links` to check for broken document links and unknown tasks (`--fix` lists new Slack channels, `--warm` prefetches titles, `--refresh-slack` updates listed and newly linked channel names using `SLACK_TOKEN` or `[slack] TOKEN`).
